# QA_Tohoku_IT_Recommender
This is the repo of the team-1 of the "Quantum Universe Lecture Series".

## 概要

適性5軸ベクトルと利用可能な総学習時間から、**限られた時間で何を学べば最も効果的か**を
QUBO ＋ アニーリングで決めるシステム。

単に「価値の高い項目を並べる」だけで済まないのは、次の3つが同時に効くからである。

1. **時間予算がある**（週28h × 27週 = 756h など）
2. **前提科目がある**（Unity を学ぶには C# が要る／機械学習には Python基礎 と 統計・数学 が要る）
3. **組み合わせ効果がある**（SQL と API設計 は相乗／Unity と Unreal Engine は非効率）

個々の項目を独立に評価できないため、**組合せ最適化問題**として解く。

## 実行方法

```
pip install -r requirements.txt
python main.py
```

### D-Wave 実機 QPU で解く

`--backend qpu` を付けると、アニーリングを Leap 経由で D-Wave の実機 QPU に投げる。

```
python main.py --backend qpu
```

事前にプロジェクト直下の `.env` へ API トークンを置く（`.env` は `.gitignore` 済み）。

```
DWAVE_API_TOKEN=DEV-xxxxxxxxxxxxxxxx
```

| オプション | 既定値 | 説明 |
| --- | --- | --- |
| `--backend` | `neal` | `neal`（ローカルSA）／`qpu`（実機） |
| `--num-reads` | `100`（neal・qpu とも） | アニーリングの実行回数 |
| `--solver` | Leap の自動選択 | QPU の機種名（例 `Advantage_system6`） |
| `--annealing-time` | `20` | 1回のアニール時間（マイクロ秒） |
| `--chain-strength` | 自動決定 | マイナー埋め込みの鎖の強さ |
| `--no-plot` | — | グラフを出さずテキスト結果だけ表示 |

QPU 実行時は、埋め込み規模・鎖切れ率・QPU アクセス時間・問題 ID がレポート末尾に出る。
QPU はマシン時間が課金対象で、実行のたびに消費する（Leap 無料枠は月1分）。

## 実験手順

[`main.py`](main.py) の単発実行に対し、複数のアンケート回答を一括でアニーリングして
結果を横断比較する**バッチ実験**は [`tools/run_all_inputs.py`](tools/run_all_inputs.py) で行う。
解の品質は検証用のスタンドアロンスクリプトで確認できる（本体パイプラインからは参照されない）。

### 1. 準備

```
pip install -r requirements.txt
```

- **入力データ**：`inputs/data/user_input_1.csv` 〜 `user_input_11.csv` を用意する。
  `inputs/data/` は `.gitignore` 済みなので各自で配置する。書式は `inputs/data/template.csv`
  と「[入力](#入力)」節を参照。
- **（QPU で回す場合のみ）**：プロジェクト直下の `.env` に自分の Leap トークンを置く。

  ```
  DWAVE_API_TOKEN=DEV-xxxxxxxxxxxx
  ```

  QPU はマシン時間が課金対象で、Leap 無料枠は月1分（→[実行方法](#実行方法)）。まずは neal で動作を確かめる。

### 2. バッチ実験の実行（`tools/run_all_inputs.py`）

リポジトリルートから実行する。既定はローカルの neal（課金なし）で、実機 QPU で回すときだけ
`--backend qpu` を明示する。グラフはウィンドウ表示せずファイルへ保存し、Windows コンソール
（cp932）でも進捗が文字化けしないよう UTF-8 で出力する。

```
python tools/run_all_inputs.py                              # neal で入力 1〜11 を一括実行
python tools/run_all_inputs.py --backend qpu                # 実機QPU で 1〜11
python tools/run_all_inputs.py --backend neal --inputs 5    # neal で入力5だけ
python tools/run_all_inputs.py --inputs 2 3 7 --num-reads 2000
```

| オプション | 既定値 | 説明 |
| --- | --- | --- |
| `--backend` | `neal` | `neal`（ローカルSA）／`qpu`（実機） |
| `--inputs` | `1〜11` | 対象の入力番号（スペース区切りで複数指定可） |
| `--num-reads` | backend の既定値（=100） | アニーリングの実行回数 |
| `--annealing-time` | config の既定値（20µs） | QPU の1回当たりのアニール時間（マイクロ秒。QPU のみ有効） |

※ このオプション表は [`main.py`](main.py) のもの（「[実行方法](#実行方法)」節）とは別物で、
バッチランナーは `--solver` / `--chain-strength` / `--no-plot` を持たない。

### 3. 出力の確認

結果は `output/result/` に書き出される（`.gitignore` 済み）。

```
output/result/
  <N>/report.txt   … 入力 N の推薦レポート全文（先頭に backend・num_reads を付与）
  <N>/graph.png    … 分野相性・項目価値の2枚グラフ
  <N>/error.txt    … その件が例外で落ちたときだけ（トレースバック）
  summary.md       … 全件横断の比較表
  summary.csv      … 同上（Excel 向けに UTF-8 BOM 付き）
```

`summary.md` / `summary.csv` の列は
**入力 / 回答者 / 状態 / 予算T(h) / 週h / 週数 / 推薦数 / 使用(h) / 目的関数値 /
QUBOエネルギー / 実行可能数 / QPU時間(µs) / 鎖切れ平均 / problem_id / 推薦項目**。
neal と QPU の解を比較したいときは、それぞれ `--backend` を変えて実行し、両方の summary を突き合わせる。

### 4. 検証ツール

> **注意**：`tools/exact_bb.py` / `tools/profile_check.py` / `main.py` は import 時に既定の

## 入力

### ユーザー入力（`inputs/data/user_input.csv`）

`key,value` 形式で、適性5軸・学習時間・学習済み科目・興味のある分野を記述する。

```
key,value
クリエイティブ,1.0
ロジカル,1.0
作る↔運用,1.0
数学,0.5
計画性・正確さ,1.0
hours_per_week,30
weeks,24
learned,"HTML/CSS, Python基礎"
interests,"フロントエンド, ゲーム開発"
```

| キー | 記号 | 内容 |
| --- | --- | --- |
| 適性5軸 | **u** ∈ [0,1]^5 | `クリエイティブ / ロジカル / 作る↔運用 / 数学 / 計画性・正確さ` |
| `hours_per_week` × `weeks` | `T` | 総学習時間（正の整数時間） |
| `learned` | `L ⊆ items` | すでに学習を終えた項目。省略可（＝空集合） |
| `interests` | `I ⊆ fields` | 興味のある分野。省略可。**表示専用で計算には使わない** |

- 適性値は `0.0`〜`1.0` の数値、または `HIGH` / `MID` / `LOW` で指定できる
  （`0.0`=低い / `0.5`=中程度 / `1.0`=高い。「作る↔運用」は `1.0`=作る側 / `0.0`=運用側）。
- `#` で始まる行と空行は無視される。
- 環境変数 `USER_INPUT_CSV` で読み込む CSV のパスを差し替えられる。

#### 学習済み科目（`learned`）

すでに学習を終えた科目を書くと、その項目は推薦されなくなる。

- 項目名は `config/items.py` の名前と一致させる（一致しない名前はエラーになる）。
  カンマ区切りで並べ、CSV の仕様上ダブルクォートで囲む。
- 学習済みの時間は予算 `T` を消費しない（過去に消費した時間として扱う）。
- 学習済みの科目は**前提科目としては満たされたものとみなす**。
  たとえば `HTML/CSS` が学習済みなら、`JavaScript/TS` を学び直さずに選べるようになる。
- 学習済みの科目とのシナジーは、相手の項目価値へ加算される（→ [実効価値](#4-学習済み科目の畳み込み)）。

#### 興味のある分野（`interests`）

アンケートで申告された興味のある分野を書くと、レポートの【興味のある分野】に
適性からの相性と併記して表示される。

- **表示だけで、推薦計算には一切使わない。** 分野は適性5軸からの相性だけで決まる。
  申告した分野が相性 0.60 未満で足切りされている場合も、そのまま並べて表示する。
  相性は分野ごとに正規化してあり（1.0 = その分野の典型像と完全一致 /
  0.0 = その分野に最も適性がない）、閾値はどの分野でも同じ意味を持つ。
- 分野名は `config/fields.py` の名前と一致させる（項目名ではなく**分野名**。
  一致しない名前はエラーになる）。

### 係数データ（`config/`）

| ファイル | 内容 | 規模 |
| --- | --- | --- |
| `config/parameters.py` | 適性5軸の定義、相性の閾値、アニーリング設定 | — |
| `config/fields.py` | 分野プロファイル `F ∈ [0,1]^{10×5}` | 10分野 × 5軸 |
| `config/items.py` | 学習項目（名前・学習時間 `h_j`・所属分野 `fields(j)`） | 38項目 / 計2,225h |
| `config/synergy.py` | 項目間シナジー `S_ij`（対称行列。正＝相乗、負＝非効率） | 72ペア（正53 / 負19。−0.7〜+0.7） |
| `config/prerequisites.py` | 前提科目。AND（全親必須）のみ | 子19項目 / 依存22本 |

## モデルの考え方

### 制約の置き場所

| 要素 | 表現 | 置き場所 |
| --- | --- | --- |
| 項目単体の価値 | 線形項 | QUBO 目的関数 |
| 組み合わせ効果（シナジー） | **二次項** | QUBO 目的関数 |
| 時間予算 | ペナルティ項（ソフト制約） | QUBO 目的関数 |
| **前提科目** | **ハード制約** | **前処理＋修復デコード** |

**負のシナジー**（同時に学ぶと非効率）は、項目を独立に評価する線形モデルでは
原理的に表現できない。二次項を持つ QUBO の必然性がここにある。

一方、**前提科目は「破ってよい度合い」が存在しない論理制約**なので、
ペナルティで抑え込むのではなく前処理で構造的に保証する
（→ [前提科目の担保](#前提科目の担保ハード制約)）。
何をペナルティにし、何をペナルティにしないかの切り分け自体が設計判断である。

### 決定変数

```
z_j ∈ {0,1}   (j ∈ C)   … 学習項目 j を学習計画に含めるか、含めないか
```

**添字は1つだけ**で、決めているのは「**どの項目を学ぶか**」という集合である。
学習の順序・時期は決めていない。前提科目も順序制約ではなく集合の包含関係であり、
`z_Unity ≤ z_C#` は「C# を先に学ぶ」ではなく「C# も選ぶ」の意味になる。
実体は**前提科目つき・シナジーつきのナップサック問題**であって、スケジューリング問題ではない。

これに加えて、予算の不等式を等式化する**スラック変数**が入る（解の意味を持たない計算上の道具）。

### 適性 u はどこに入るか

目的関数 `E(z)` の式に `u` は現れないが、**前処理で項目価値 `V_j(u)` と
候補集合 `C(u)` に畳み込まれている**。

| | 適性 `u` への依存 |
| --- | --- |
| 線形係数 `V_j(u)` | **依存する**（ユーザーごとに変わる） |
| **候補集合 `C(u)`** | **依存する**（価値0の項目は候補外） |
| 二次係数 `S_ij` | 依存しない（全ユーザー共通） |
| 予算制約・前提科目 | 依存しない |

適性は係数だけでなく**問題サイズそのものを変える**。逆にこの設計では、適性は
「組み合わせの好み」には影響しない（誰にとっても SQL × API設計 は +0.7）。

## 処理フロー

```
適性5軸 u
  ↓
各IT分野との相性 fs
  ↓
低相性分野（min_relevance 未満）の寄与を除外 → fr
  ↓
所属分野の相性を合計して学習項目価値 V を計算
  ↓
学習済み科目 L を候補から除外し、実効前提 P' と実効価値 V' へ畳み込む
  ↓
候補集合の生成 ＋ 前提科目の前処理（予算枝刈り・候補展開）
  ↓
時間を最大公約数で圧縮
  ↓
予算制約・シナジー・条件付き価値を QUBO 化（前提科目のペナルティ項は無し）
  ↓
アニーリング
  ↓
修復デコード（前提未達の子を除去 / 不足親を補完）
  ↓
真の目的関数値（価値＋シナジー）が最大の実行可能解を推薦
```

以下の番号は [`calculation/recommend.py`](calculation/recommend.py) 内のセクション番号に対応する。

### 1. 分野相性 `fs`

5軸を等重みとした平均二乗距離から相性を求める（完全一致=1）。

```
fs_f = clip( 1 − (1/5) · Σ_a (F_{f,a} − u_a)² , 0, 1 )      （f = 各分野）
```

### 2. 低相性分野の除外 `fr`

閾値 θ = `min_relevance` = **0.80**（`config/parameters.py: DEFAULT_MIN_RELEVANCE`）。

```
fr_f = fs_f   (fs_f ≥ θ)
     = 0      (fs_f < θ)
```

すべての `fr_f` が 0 の場合は推薦不能（エラー）。

### 3. 学習項目価値 `V`

項目が所属する分野の関連度を合計する。複数の関連分野で使える項目ほど高価値になる。

```
V_j = Σ_{f ∈ fields(j)} fr_f
```

`Git` は5分野、`開発環境/ターミナル` は4分野に属するため、この構造で上位に来やすい。

### 4. 学習済み科目の畳み込み

学習済み集合 `L` を「**決定変数 `z_j = 1` に固定して QUBO から消した項目**」とみなす。
前提・シナジー・候補集合の扱いはすべてこの一点から導く。
ただし本モデルの時間と価値は「**これから**学ぶ分」だけを数えるため、通常の変数固定と2点だけ異なる。

| | 通常の変数固定 | 本モデル |
| --- | --- | --- |
| 時間 | 固定分を予算から差し引く | **差し引かない**（過去に消費済み。`T` は今後の予算） |
| 価値 | 固定分を定数項として加算 | **加算しない**（目的関数値＝これから得る価値） |

したがって `L` の項目は QUBO の変数にもならず、予算式にも目的関数にも現れない。
残るのは次の2つの効果だけである。

**実効前提 `P'`**（前提の解放）

```
P'(c) = P(c) \ L        （c ∉ L）
```

`P'(c) = ∅` になった子は「前提のない項目」として扱われ、価値は条件付き二次項ではなく
線形項へ戻る。前提クロージャも `P'` で計算する。
`config/prerequisites.py` の定義自体は書き換えず、実行時に畳んだ辞書を作る。

**実効価値 `V'`**（シナジーの畳み込み）

二次項 `S_ij z_i z_j` に `z_i = 1 (i ∈ L)` を代入すると `S_ij z_j`、つまり項目 `j` の
線形ボーナスに落ちる。これを項目価値へ畳み込む。

```
B_j  = Σ_{i ∈ L} S_ij            （学習済みシナジーの合計。負にもなりうる）
V'_j = V_j + B_j                 （実効価値）
```

負のシナジーも畳み込む。「同時学習の非効率」は「重複スキルの冗長性」でもあり、
既習との関係でも成立するとみなす。

**学習済みが前提を満たしていない場合**（「Unity は済だが C# は未習」といった自己申告の不整合）は、
**警告を1行出して続行する**。学習済みは「その項目自身」だけを満たし、前提へは伝播しない。
未習の親は候補に残り、価値があれば推薦されうる。クロージャを自動補完して学習済み扱いにはしない
（学んでいない科目を永久に推薦対象から外すのは、除外の副作用として重すぎるため）。

### 5. 候補集合 `C`

```
C = ( { j : V_j > 0 } \ L )
      → 予算枝刈り（minClosureHours'(j) > T を除外）
      → 実効前提 P' で候補展開（前提科目を候補へ追加）
```

- **候補入りの判定には元の分野価値 `V_j` を使う**（実効価値 `V'_j` ではない）。
  学習済みシナジーのボーナスだけを理由に、閾値未満の分野の項目が候補へ紛れ込むのを防ぐため。
- **予算枝刈り**：前提クロージャ込みの最小学習時間が予算を超える項目を外す。

  ```
  minClosureHours'(j) = 項目 j の前提クロージャ（j 自身を含み、L は除く）の合計時間
  ```

  AND前提のみなのでクロージャは項目ごとに**一意**に定まり、選択肢による分岐はない。
  共有された親は集合として1回だけ計上する。この条件を満たす項目はどう選んでも
  「前提充足かつ予算内」の解に現れないため、除外しても最適性を損なわない。
- 枝刈りは**候補展開の前に1回だけ**行う。追加される親のクロージャは子のクロージャの
  部分集合（`closure'(parent) ⊆ closure'(child)`）なので、子が枝刈りを通っていれば
  親の最小クロージャ時間も必ず `T` 以下になるためである。
- 学習済みの除外は候補を**減らすとは限らない**。前提が解放されてクロージャ時間が縮み、
  これまで枝刈りされていた項目が予算内に入ることがある。
- `C = ∅` は `RuntimeError`。メッセージには予算 `T` と最小クロージャ時間を含め、
  「予算不足」か「学習済みで尽きた」かを区別できるようにしてある。

### 6. 時間の圧縮

QUBO 規模削減のため最大公約数で単位化する。

```
g   = gcd( T, { h_j : j ∈ C } )
c_j = h_j / g          （項目コスト）
B   = T / g            （予算）
```

スラック変数の個数が減るだけでなく、**予算ペナルティ項の係数の桁が下がる**効果がある
（予算制約の二次項は係数の積で効くため、数値的な安定性に直結する）。

ただし効くのは `T` と候補項目の時間が共通の約数を持つときだけである。
現在の `config/items.py` には 25h・35h の項目があるため、`T` によっては `g = 1` となり
圧縮が働かない（レポートの【時間圧縮単位】で実際の `g` を確認できる）。

### 7. QUBO の目的関数

決定変数 `z_j ∈ {0,1}`（j ∈ C）、スラック `s = Σ_k w_k y_k`（`y_k ∈ {0,1}`）。
最小化するエネルギー：

```
E(z) = − Σ_{j∈C, P'(j)=∅} V'_j · z_j                              … 線形項（項目価値）
       − Σ_{c∈C, P'(c)≠∅} V'_c · z_c · ( Σ_{p∈P'(c)} z_p − (n'−1) )  … 条件付き価値、n' = |P'(c)|
       − Σ_{i<j∈C} S_ij · z_i · z_j                               … 二次項（シナジー。負値も可）
       + A · ( Σ_{j∈C} c_j · z_j + s − B )²                       … 予算制約
```

- **前提科目のペナルティ項は存在しない。** 担保は
  [前提科目の担保](#前提科目の担保ハード制約) の機構が行う。
- 二次項は `i<j` で走る（`S` は対称行列なので `Σ_{i,j}` と書くと二重計上になる）。

**条件付き価値 `G_c`**：前提科目を持つ子 `c` の価値は線形項ではなく、
「前提が揃って初めて発生する価値」として親との二次項で表現する。

```
G_c = V'_c · z_c · ( Σ_{p∈P'(c)} z_p − (n'−1) )

    全親を選択 → V'_c（満額）／親が1つ欠ける → 0／さらに欠ける → 負（損）
```

AND前提のみなので、この表現は近似ではなく「前提が揃ったとき、かつそのときだけ満額」を
**厳密に**表す。係数は価値 `V'` スケールでありペナルティ係数 `A` は使わないため、
エネルギー地形が巨大な制約項に支配されることがない。
条件付き価値は**探索の誘導のみ**を担い、前提充足の担保には関与しない。

学習済みシナジー `B_c` も条件付き価値の側に含める（`V'_c` ごと二次項にする）。
`B_c` だけを無条件の線形項にすると、前提未達のまま子を立てるとボーナスだけ得られる形になり、
探索の誘導が濁るためである。

**予算制約のスラック化**：QUBO は等式制約しか自然に表せないため、スラック変数を導入する。

```
Σ c_j z_j ≤ B    →    Σ c_j z_j + s = B    →    A · ( Σ c_j z_j + s − B )²
```

`s` の重みは `bounded_binary_weights(B)`（`calculation/encoding.py`）で決める。
単純な2冪だと上限 `B` を超える値まで表せて無駄が出るため、**上限で打ち切る**
（例：`B = 24` に対し `[1, 2, 4, 8, 9]` の5変数で 0〜24 を過不足なく表現する）。

**ペナルティ係数 `A`**（予算制約専用）

```
A = max_{j∈C} ( max(0, V'_j) + Σ_{i∈C} max(0, S_ij) ) × ( 1 + penalty_margin )
    └────── 単一項目の限界寄与 ──────┘             └ 既定 0.01 ┘
```

「**違反を防ぐのに必要な最小値**」から決める。予算を1単位超えた解からは、
他の選択項目の前提になっていない項目（前提DAGの極大元。選択が空でなければ必ず存在する）を
1つ除去すれば、子の条件付き価値を巻き添えにせず実行可能化できる。
そのとき失う報酬の主要項が単一項目の限界寄与 `V'_j + Σ_i max(0, S_ij)` になる。
`penalty_margin` は実行可能解と1単位違反解が同点になるのを避けるための微小マージン。

AND前提のみなので、この限界寄与は**厳密な上界**である（親が揃ったときの子の報酬が
ちょうど `V'_c` で頭打ちになるため）。したがって「`A >` 限界寄与 なら1単位違反の解は
必ず実行可能解に負ける」と主張できる。

### 8. アニーリング

- 既定サンプラー：`neal.SimulatedAnnealingSampler`
  （`num_reads=100`, `num_sweeps=5000`, `seed=42`。`config/parameters.py`）。
- D-Wave QPU 等の外部サンプラーを注入可能（`recommend(..., sampler=..., sampler_kwargs=...)`）。
- **実機 QPU 実行**（`--backend qpu`）では `EmbeddingComposite(DWaveSampler())` に切り替わる
  （`calculation/sampler.py`）。API トークンは `.env` の `DWAVE_API_TOKEN` から読む。
  既定は `num_reads=100`, `annealing_time=20µs`, `answer_mode="raw"`
  （既定の `histogram` は同一サンプルを集約してしまい、neal とサンプル数を比較できないため）。
  鎖の強さは `uniform_torque_compensation` による自動決定。

### 9. 修復デコードと解の採用

アニーリングの**最低エネルギー解をそのまま採用してはいけない**。低エネルギー側にも
制約違反解が混ざるためである。各サンプルは次の手順で採用候補にする。

1. **下方修復**（`repair_prerequisites`）：前提未達の子項目を、すべて満たされるまで取り除く。
   AND制約は親の選択に対して単調なので、除去の順序によらず「元の選択に含まれる
   最大の実行可能部分集合」に収束する。項目を取り除くだけなので予算を新たに破ることはない。
2. **上方補完**（`complete_prerequisites`）：前提が欠けていたサンプルには、不足親をすべて
   追加する補完も試す。予算に収まる場合のみ候補に加える（高価値の子を捨てずに済む解を拾うため）。
3. **予算検査**：修復後の選択に対して `Σ h_j z_j ≤ T` を検査する。

修復後の選択は**定義上すべて前提科目制約を満たす**ため、前提違反を理由にサンプルが
捨てられることはない。残る検査は予算のみになる。

順位付けは QUBO エネルギーではなく、修復後の**真の目的関数値**で行う。

```
score(z) = Σ_{j∈C} V'_j z_j + Σ_{i<j∈C} S_ij z_i z_j
```

エネルギーは修復前のビット列に対応する値であり、修復で項目が除かれると実際の価値と
ずれるためである。同値なら合計時間が短い方を採る（価値0の項目だけを足した冗長な解を除くため）。
予算内の解が1つも無ければエラー。

### 10. 最終検査と出力

- **最終検査**：`Σ h_j z_j ≤ T` および前提科目（`check_prerequisites`）を再確認する。
- **テキストレポート**（`output/report.py`）：適性・興味・学習時間・学習済み・分野相性・
  推薦項目（価値の内訳／前提／シナジー）・合計時間・報酬上限・ペナルティ係数・
  実行可能サンプル数・目的関数値・QUBOエネルギー・実行基盤の情報。
- **グラフ2枚**（`output/visualize.py`）：① 分野相性 ② 項目価値。
  QUBOエネルギーの分布は「アニーリングがどう動いたか」の図であって「何を学べばよいか」の
  図ではないため、可視化からは外してある（エネルギーの値はテキストに残る）。

## 前提科目の担保（ハード制約）

前提科目制約は**ハード制約**であり、**QUBO の目的関数（ペナルティ項）には含めない**。
`calculation/prerequisites.py` が次の3段階で構造的に担保する。

| 段階 | 内容 | 関数 |
| --- | --- | --- |
| ① 候補集合の制限（前処理） | 予算内で前提を満たせない項目を候補から外す | `restrict_candidates_by_budget` |
| ② 候補展開（前処理） | 候補項目が必要とする前提科目を候補へ追加する | `add_prerequisites_to_candidates` |
| ③ 修復デコード（求解後） | 各サンプルを前提充足の選択へ変換する | `repair_prerequisites` / `complete_prerequisites` |

修復後の選択は定義上すべて前提科目制約を満たすため、**前提違反の解が最終候補に現れることは
構造的にない**。条件付き価値（`G_c`）は探索の誘導のみを担い、担保には関与しない。

**難所**：前提科目は予算制約と結合する（子を選ぶと親の `hours` も消費する）ため、
単純な事前確定はできない。①で「前提クロージャ込みの最小時間」を使うことでこれを解いている。

**設計上の留意点への対応**

- **予算制約との結合**：予算検査は修復後の選択に対して行う。下方修復は時間を増やさず、
  上方補完は予算超過なら候補にしないため、担保が予算と衝突しない。
- **親の共有**：前処理・デコードとも集合ベースの操作なので、コストの二重計上は起きない。
- **循環の検査**：AND前提に循環があるとクロージャの計算が停止しないため、
  `validate_prerequisite_data()` が起動時に循環を検査する。

| 前提科目（AND） | 依存関係の担保 | 親を全て選ぶ。ペナルティ項は持たない | 前処理＋修復デコード |

## 設計上の既知の制約

- **弱い依存がモデル上どこにも無い。** 「Git を選ぶなら言語を1つ以上やっていること」
  のような依存は、必須性が低くハード制約にできないため AND 前提から外してある。
  結果として、モバイル言語を1つも選ばずに `モバイルUI` を選ぶ解などが実行可能になっている。
  シナジー `S_ij` として入れ直すか、必須性の高いものは AND 前提へ移すかは未決。
- **予算 `T` が最小クロージャ時間に届かないケース。** 候補が0件になり `RuntimeError` で
  落ちる（エラーメッセージに予算と必要時間を出している）。部分学習・最小コスト項目の提示
  といったフォールバックは未実装。
- **興味 `I` は目的関数に入らない。** 自己申告と適性由来の相性をどう重み付けるかは
  係数設計の問題として残してある。
- **分野プロファイル・シナジー係数は仮の目安。** 根拠となるデータ（求人票の共起頻度など）が
  得られたら差し替えることを想定している。

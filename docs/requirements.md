# モデル要件定義（issue #1 確定版）

本ドキュメントは GitHub issue #1「Feat: モデルの要件定義」の確定版要件である。
QUBO／アニーリングによる学習項目推薦モデルの入力・前処理・目的関数・制約・求解・出力を数式レベルで定義する。

> 前提科目の前処理化（第3.5節）は issue #5 で実装済み。流行項の追加は未実装（第8節）。
> **OR 前提は廃止した**（第3.5節・第9節）。前提科目は AND（全親必須）のみである。

---

## 1. 背景・目的

適性5軸ベクトルと利用可能な総学習時間から、時間予算・前提科目・シナジーを考慮して
最適な学習項目集合を選ぶモデル。データフローは以下。

```
適性5軸 u
  ↓
各IT分野との相性 fs
  ↓
低相性分野（min_relevance未満）の寄与を除外 → fr
  ↓
所属分野の相性を合計して学習項目価値 V を計算
  ↓
候補集合の生成 ＋ 前提科目の前処理（予算枝刈り・候補展開）
  ↓
予算制約・シナジー・条件付き価値を QUBO 化（前提科目のペナルティ項は無し）
  ↓
アニーリング
  ↓
修復デコード（前提未達の子を除去 / 不足親を補完）
  ↓
真の目的関数値（価値＋シナジー）が最大の実行可能解を推薦
```

issue #1 本文の表は当初「線形項 / 二次項 / 予算制約」の3項のみを記載していたが、
実際には分野相性フィルタと前提科目制約も存在する。本ドキュメントで全体を確定する。

---

## 2. 入力

### ユーザー入力（`inputs/data/user_input.csv`、`inputs/user_input.py`）
- 適性5軸ベクトル **u** ∈ [0,1]^5。軸は
  `クリエイティブ / ロジカル / 作る↔運用 / 数学 / 計画性・正確さ`。
  値は 0.0–1.0 または `HIGH(1.0) / MID(0.5) / LOW(0.0)`。
  「作る↔運用」は 1.0=作る側 / 0.0=運用側。
- 総学習時間 `T = hours_per_week × weeks`（正の整数時間）。

### 係数データ（`config/`）
- 分野プロファイル `F ∈ [0,1]^{10×5}`（`config/fields.py`、10分野 × 5軸）。
- 学習項目（`config/items.py`）: 項目ごとに hours `h_j` と所属分野 `fields(j)`。項目数 `M`。
- シナジー `S_ij`（`config/synergy.py`、対称行列。正＝相乗、負＝非効率）。
- 前提科目（`config/prerequisites.py`）: AND前提のみ（15件）。

## 3. 前処理（Preprocessing）

### 3.1 分野相性
5軸を等重みとした平均二乗距離から相性を求める（完全一致=1）。

```
fs_f = clip( 1 − (1/5) · Σ_a (F_{f,a} − u_a)² , 0, 1 )      （f = 各分野）
```

### 3.2 低相性分野の除外
閾値 θ = `min_relevance` = **0.60**（`config/parameters.py: DEFAULT_MIN_RELEVANCE`）。

```
fr_f = fs_f   (fs_f ≥ θ)
     = 0      (fs_f < θ)
```
すべての `fr_f` が 0 の場合は推薦不能（エラー）。

### 3.3 学習項目価値
項目が所属する分野の関連度を合計する（複数の関連分野で使える項目ほど高価値）。

```
V_j = Σ_{f ∈ fields(j)} fr_f
```

### 3.4 候補集合
```
C = （ { j : V_j > 0 }  ∪  前提科目クロージャ ）から予算枝刈りした集合
```
- 価値0でも、候補項目の前提科目は候補へ追加する（既存 `add_prerequisites_to_candidates`）。
- **予算枝刈り**: 最小クロージャ時間 `minClosureHours(j) > T` の項目を候補から除外する
  （`restrict_candidates_by_budget`）。

  ```
  minClosureHours(j) = 項目 j の前提クロージャ（j 自身を含む）の合計時間
  ```

  AND前提のみなのでクロージャは項目ごとに**一意**に定まり、選択肢による分岐はない
  （`prerequisite_closure`）。共有された親は集合として1回だけ計上する。
  この条件を満たす項目はどう選んでも「前提充足かつ予算内」の解に現れないため、
  除外しても最適性を損なわない。

  枝刈りは**候補展開の前に1回だけ**行う。追加される親のクロージャは子のクロージャの
  部分集合なので、子が枝刈りを通っていれば親の最小クロージャ時間も必ず T 以下になり、
  展開後に枝刈りをやり直す必要がないためである
  （OR前提があった頃は、選択肢として追加した項目が単独では予算に収まらない場合があり、
  展開の前後に1回ずつ枝刈りが必要だった）。

### 3.5 前提科目のハード制約担保 ★確定要件（issue #5 で実装済み）
前提科目制約は**ハード制約**であり、**QUBO の目的関数（ペナルティ項）には含めない**。

- AND前提: 子を選ぶなら親を**すべて**選ぶ（`z_child ≤ z_parent`）。**前提科目はこの1種類のみ。**

**担保機構**（実装: `calculation/prerequisites.py`）は次の3段階。

1. **候補集合の制限（前処理）**: 予算内で前提を満たせない項目を候補から除外する（第3.4節の予算枝刈り）。
2. **候補展開（前処理）**: 候補項目が必要とする前提科目を候補へ追加する。
3. **修復デコード（求解後）**: アニーリングの各サンプルを前提充足の選択に変換する。
   - **下方修復**（`repair_prerequisites`）: 前提未達の子項目を、すべて満たされるまで取り除く。
     AND制約は親の選択に対して単調なので、除去の順序によらず
     「元の選択に含まれる最大の実行可能部分集合」に収束する。
     項目を取り除くだけなので予算制約を新たに破ることはない。
   - **上方補完**（`complete_prerequisites`）: 前提が欠けていたサンプルには、
     不足親をすべて追加する補完も試す。予算に収まる場合のみ解の候補に加える。

   修復後の選択は**定義上すべて前提科目制約を満たす**ため、
   前提違反の解が最終候補に現れることは構造的にない。

子項目の価値は「前提が揃って初めて発生する条件付き価値」（第4節）として QUBO に残るが、
これは探索の誘導のみを担い、制約の担保には関与しない。

> 設計上の留意点への対応:
> - **予算制約との結合**: 予算検査は修復後の選択に対して行う。下方修復は時間を増やさず、
>   上方補完は予算超過なら候補にしないため、担保が予算と衝突しない。
> - **親の共有**: 前処理・デコードとも集合ベースの操作なので、コストの二重計上は起きない。
> - **循環の検査**: AND前提に循環があるとクロージャの計算が停止しないため、
>   `validate_prerequisite_data()` が起動時に循環を検査する。

### 3.6 時間の圧縮
QUBO 規模削減のため最大公約数で単位化する。

```
g   = gcd( T, { h_j : j ∈ C } )
c_j = h_j / g          （項目コスト）
B   = T / g            （予算）
```

## 4. 目的関数（QUBO）

決定変数 `z_j ∈ {0,1}`（j ∈ C）、スラック `s = Σ_k w_k y_k`（`y_k ∈ {0,1}`）。
最小化するエネルギー:

```
E(z) = − Σ_{j∈C, 前提なし} V_j · z_j                 … 線形項（項目価値の最大化）
       − Σ_{c∈C, 前提あり} G_c(z)                    … 条件付き価値（下記）
       − Σ_{i<j∈C} S_ij · z_i · z_j                 … 二次項（シナジー。S_ij < 0 の負相関も含む）
       + A · ( Σ_{j∈C} c_j · z_j + s − B )²         … 予算制約（スラック変数で等式化）
```

- **前提科目のペナルティ項・ORスラック変数（or_slack_*）は存在しない**（第3.5節の機構で担保）。
- **条件付き価値 G_c(z)**: 前提科目を持つ子 c の価値 `V_c` は線形項ではなく、
  「前提が揃って初めて発生する価値」として親との二次項で表現する。

  ```
  AND前提（親 p_1..p_n）: G_c = V_c · z_c · ( Σ_p z_p − (n−1) )
      全親を選択 → V_c（満額）／親が1つ欠ける → 0／さらに欠ける → 負（損）
  ```

  AND前提のみなので、この表現は近似ではなく「前提が揃ったとき、かつそのときだけ満額」を
  **厳密に**表す（OR前提があった頃は、選択肢数に比例させる近似項 `V_g/min(m,2)` が
  別に必要で、価値を2グループへ均等割りする処理も伴っていた）。

  係数は価値 V スケールであり、ペナルティ係数 A は使わない。
  条件付き価値は**探索の誘導のみ**を担い、前提充足の担保（第3.5節）には関与しない。
  そのためエネルギー地形が巨大な制約項に支配されない。
- スラック重み `w = bounded_binary_weights(B)`（`calculation/encoding.py`）で 0..B の整数を表現。
- ペナルティ係数（予算制約専用）

  ```
  A = max_j ( V_j + Σ_i max(0, S_ij) ) × ( 1 + penalty_margin )
      └─ 単一項目の限界寄与 ─┘         └ 既定 0.01（config/parameters.py）
  ```

  「違反を防ぐのに必要な最小値」から決める（issue #8）。予算を1単位超えた解からは、
  他の選択項目の前提になっていない項目（前提DAGの極大元。選択が空でなければ必ず存在する）を
  1つ除去すれば子の条件付き価値を巻き添えにせず実行可能化でき、そのとき失う報酬の主要項が
  単一項目の限界寄与 `V_j + Σ_i max(0, S_ij)` になる。`penalty_margin` は
  実行可能解と1単位違反解が同点になるのを避けるための微小マージン。

  旧式 `A = ( Σ_j max(0, V_j) + Σ_{S_ij>0} S_ij ) + 1 = 30.050` は「1単位の超過で
  全報酬が消える」ほど過大で、目的項の差 0.15〜2.4 に対し1〜2桁大きかった。
  現行は **A = 2.424** で目的項と同じ桁になっている。

  OR前提の廃止により、この限界寄与は**厳密な上界**になった。条件付き価値が AND のみと
  なり、親が揃ったときの子の報酬がちょうど `V_c`（満額）で頭打ちになるためである。
  したがって「`A >` 限界寄与 なら1単位違反の解は必ず実行可能解に負ける」と主張できる
  （OR前提があった頃は親を k 個選んだ子の報酬が `V_j · k / min(m,2)` まで膨らみ、
  限界寄与を上回りうるためこの保証がなかった）。

## 5. 求解（Solving）

- 既定サンプラー: `neal.SimulatedAnnealingSampler`
  （`num_reads=5000`, `num_sweeps=5000`, `seed=42`。`config/parameters.py`）。
- D-Wave QPU 等の外部サンプラーを注入可能
  （`recommend(..., sampler=..., sampler_kwargs=...)`）。
- **実機 QPU 実行**: `python main.py --backend qpu` で
  `EmbeddingComposite(DWaveSampler())` に切り替わる（`calculation/sampler.py`）。
  API トークンは `.env` の `DWAVE_API_TOKEN` から読む。
  既定は `num_reads=1000`, `annealing_time=20µs`, `answer_mode="raw"`
  （既定の `histogram` は同一サンプルを集約してしまい、neal とサンプル数を比較できないため）。
  鎖の強さは `uniform_torque_compensation` による自動決定。
- **実機での実測**（Advantage_system6, 適性 = `user_input.csv` の既定値, T=720h）
  ※ **OR前提の廃止前に測定した値**であり、再測定が必要（第8節）:
  34 変数の完全グラフ K34 が物理量子ビット 161〜173 個へ埋め込まれ
  （鎖長 平均 4.7〜5.1／最大 7）、QPU アクセス時間は 1000 リードで 0.13 秒。
  目的関数値は 15.6〜16.0 で、当時の厳密最適 18.650 に対する達成率は **84〜86%**
  （neal は 17.950／96.2%）。`num_reads` を 1000 → 5000 に増やしても改善せず、
  ボトルネックはサンプル数ではない。
  変数数・二次項数・ダイナミックレンジは OR 廃止後も変わらない（34 変数／二次項 561／896 倍）
  ため、埋め込みと鎖切れに関する所見はそのまま有効である。
  - **鎖切れ率が平均 9〜12%、鎖切れゼロのサンプルは 0.1% 未満**。
    多数決補正が入るため、実機のサンプルは論理 QUBO の解として信頼度が落ちる。
  - **QUBO 係数のダイナミックレンジが 896 倍**（予算制約ペナルティは
    重み 32 のスラック変数と掛かって数千、項目価値は 1 前後）。
    QPU は最大絶対値が 1 になるよう自動スケールしてから磁束を印加するので、
    項目価値の差が制御誤差（ICE）に埋もれる。倍精度で計算する neal では起きない。

## 6. 後処理・出力

- **修復デコード**: 各サンプルを下方修復（前提未達の子を除去）し、前提が欠けていた
  サンプルには上方補完（不足親の追加。予算内の場合のみ）も試す（第3.5節）。
  修復後の選択はすべて前提科目制約を満たすため、前提違反でサンプルが捨てられることはない。
- **実行可能解の抽出**: 修復後の選択に対して予算（`Σ h_j z_j ≤ T`）を検査し、
  **真の目的関数値** `Σ V_j z_j + Σ S_ij z_i z_j` が最大の解を採用する
  （同値なら合計時間が短い方）。QUBO エネルギーは修復前のビット列に対応する値であり、
  修復で項目が除かれると実際の価値とずれるため、順位付けには使わない。
  予算内の解が1つも無ければエラー。
- **最終検査**: `Σ h_j z_j ≤ T` および前提科目（`check_prerequisites`）の再確認。
- **出力**: テキストレポート（`output/report.py`）＋ グラフ（`output/visualize.py`）。

## 7. 確定した制約項の一覧（issue #1 表の更新版）

| 種別 | 目的 | 詳細 | 位置づけ |
| -- | -- | -- | -- |
| 線形項 V_i | 単体項目の価値最大化 | 適性相性 0.60 未満の分野は寄与を除外。前提を持たない項目のみ | QUBO 目的関数 |
| 条件付き価値 G_c | 前提充足時のみ子の価値を計上 | AND=全親で満額（近似なし）。係数は V スケール | QUBO 目的関数（探索誘導のみ） |
| 二次項 S_ij | シナジー（相乗効果） | 「Unity と Unreal Engine」等の負の相関も考慮 | QUBO 目的関数 |
| 予算制約 P_budget | 学習時間の上限 | スラック変数を導入し不等式を等式化。ペナルティ係数 A を使う唯一の制約 | QUBO 目的関数 |
| 分野相性フィルタ | 低相性分野・無価値項目の除外 | 相性 0.60 未満の分野寄与を 0、価値0項目を候補外に | 前処理 |
| 予算枝刈り | 予算内で前提を満たせない項目の除外 | minClosureHours(j) > T の項目を候補外に | 前処理 |
| 前提科目（AND） | 依存関係の担保 | 親を全て選ぶ。ハード制約。ペナルティ項・ORスラックは廃止 | **前処理＋修復デコード**（★実装済み） |

## 9. OR前提の廃止（本改訂）

前提科目のうち **OR前提（`z_child ≤ Σ z_parents`、8件）を廃止**し、AND前提のみとした。

**廃止した OR 関係**

| 子項目 | 選択肢だった親 |
| -- | -- |
| SQL/データベース | バックエンド言語 / Python基礎 |
| アルゴリズム | バックエンド言語 / Python基礎 / C# / C++ |
| モバイルUI | Swift/Kotlin / Flutter/RN |
| アプリ設計 | Swift/Kotlin / Flutter/RN |
| ゲーム数学・物理 | C# / C++（AND前提「アルゴリズム」は残る） |
| 3Dグラフィックス | C# / C++ |
| Git | JavaScript/TS / バックエンド言語 / Swift/Kotlin / Flutter/RN / Python基礎 |
| 開発環境/ターミナル | JavaScript/TS / バックエンド言語 / Swift/Kotlin / Flutter/RN |

**廃止の理由**

1. これらは「必ず必要」ではなく「あると効く」弱い依存であり、
   本来はハード制約ではなくシナジー `S_ij` で表すべき関係だった。
2. 条件付き価値の分母 `min(m,2)` が近似でしかなく、探索の誘導が偏っていた（旧第8節）。
3. 予算枝刈り・修復デコードの分岐処理の大半が OR 側にあった。

**モデルへの影響**

| | OR 廃止前 | OR 廃止後 |
| -- | -- | -- |
| 条件付き価値 | AND は厳密／OR は近似 | **すべて厳密**（近似項なし） |
| ペナルティ係数 A の根拠 | 限界寄与は厳密な上界ではない | **厳密な上界**（第4節） |
| 予算枝刈り | 候補展開の前後に2回 | **前に1回**（第3.4節） |
| 前提クロージャ | 選択肢ごとに分岐して最小値を探索 | **一意に定まる**（第3.4節） |
| QUBO 規模 | 34変数 / 二次項 561 | **変化なし**（34変数 / 二次項 561） |

QUBO 規模が変わらないのは、予算制約のペナルティ項が全変数ペアに二次項を張るため、
OR 由来の二次項を除いてもペアの**本数**は変わらず係数だけが変わるからである。

**副作用（要注意）**: OR前提が禁じていた選択が実行可能になった。
デモ条件の厳密最適解は `モバイルUI` を Swift/Kotlin・Flutter/RN のどちらも選ばずに含む。
「モバイル言語を学ばずにモバイルUIを学ぶ」学習計画は推薦として不自然であり、
第8節のとおり再表現の要否を検討する必要がある。

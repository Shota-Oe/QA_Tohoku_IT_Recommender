# モデル要件定義（issue #1 確定版）

本ドキュメントは GitHub issue #1「Feat: モデルの要件定義」の確定版要件である。
QUBO／アニーリングによる学習項目推薦モデルの入力・前処理・目的関数・制約・求解・出力を数式レベルで定義する。

> 前提科目の前処理化（第3.5節）は issue #5 で実装済み。流行項の追加は未実装（第8節）。
> **OR 前提は廃止した**（第3.5節・第9節）。前提科目は AND（全親必須）のみである。
> **学習済み科目の除外（第10節）は実装済み。** 第2〜7節の記述は
> 学習済み集合 L = ∅ のときの姿であり、L ≠ ∅ の場合の差分は第10節にまとめてある。

---

## 1. 背景・目的

適性5軸ベクトルと利用可能な総学習時間から、時間予算・前提科目・シナジーを考慮して
最適な学習項目集合を選ぶモデル。データフローは以下。

```
適性5軸 u
  ↓
各IT分野との相性 fs
  ↓
低相性分野（min_relevance未満）の寄与を除外 → fr
  ↓
所属分野の相性を合計して学習項目価値 V を計算
  ↓
候補集合の生成 ＋ 前提科目の前処理（予算枝刈り・候補展開）
  ↓
予算制約・シナジー・条件付き価値を QUBO 化（前提科目のペナルティ項は無し）
  ↓
アニーリング
  ↓
修復デコード（前提未達の子を除去 / 不足親を補完）
  ↓
真の目的関数値（価値＋シナジー）が最大の実行可能解を推薦
```

issue #1 本文の表は当初「線形項 / 二次項 / 予算制約」の3項のみを記載していたが、
実際には分野相性フィルタと前提科目制約も存在する。本ドキュメントで全体を確定する。

---

## 2. 入力

### ユーザー入力（`inputs/data/user_input.csv`、`inputs/user_input.py`）
- 適性5軸ベクトル **u** ∈ [0,1]^5。軸は
  `クリエイティブ / ロジカル / 作る↔運用 / 数学 / 計画性・正確さ`。
  値は 0.0–1.0 または `HIGH(1.0) / MID(0.5) / LOW(0.0)`。
  「作る↔運用」は 1.0=作る側 / 0.0=運用側。
- 総学習時間 `T = hours_per_week × weeks`（正の整数時間）。
- **学習済み集合 `L ⊆ items`**（`learned` キー。省略可＝空集合）。
  すでに学習を終えた項目。前処理で候補から除外する（**第10節**）。

### 係数データ（`config/`）
- 分野プロファイル `F ∈ [0,1]^{10×5}`（`config/fields.py`、10分野 × 5軸）。
- 学習項目（`config/items.py`）: 項目ごとに hours `h_j` と所属分野 `fields(j)`。項目数 `M`。
- シナジー `S_ij`（`config/synergy.py`、対称行列。正＝相乗、負＝非効率）。
- 前提科目（`config/prerequisites.py`）: AND前提のみ（前提を持つ子項目20件／依存23本）。

## 3. 前処理（Preprocessing）

### 3.1 分野相性
5軸を等重みとした平均二乗距離から相性を求める（完全一致=1）。

```
fs_f = clip( 1 − (1/5) · Σ_a (F_{f,a} − u_a)² , 0, 1 )      （f = 各分野）
```

### 3.2 低相性分野の除外
閾値 θ = `min_relevance` = **0.60**（`config/parameters.py: DEFAULT_MIN_RELEVANCE`）。

```
fr_f = fs_f   (fs_f ≥ θ)
     = 0      (fs_f < θ)
```
すべての `fr_f` が 0 の場合は推薦不能（エラー）。

### 3.3 学習項目価値
項目が所属する分野の関連度を合計する（複数の関連分野で使える項目ほど高価値）。

```
V_j = Σ_{f ∈ fields(j)} fr_f
```

### 3.4 候補集合
```
C = （ { j : V_j > 0 }  ∪  前提科目クロージャ ）から予算枝刈りした集合
```
- 価値0でも、候補項目の前提科目は候補へ追加する（既存 `add_prerequisites_to_candidates`）。
- **予算枝刈り**: 最小クロージャ時間 `minClosureHours(j) > T` の項目を候補から除外する
  （`restrict_candidates_by_budget`）。

  ```
  minClosureHours(j) = 項目 j の前提クロージャ（j 自身を含む）の合計時間
  ```

  AND前提のみなのでクロージャは項目ごとに**一意**に定まり、選択肢による分岐はない
  （`prerequisite_closure`）。共有された親は集合として1回だけ計上する。
  この条件を満たす項目はどう選んでも「前提充足かつ予算内」の解に現れないため、
  除外しても最適性を損なわない。

  枝刈りは**候補展開の前に1回だけ**行う。追加される親のクロージャは子のクロージャの
  部分集合なので、子が枝刈りを通っていれば親の最小クロージャ時間も必ず T 以下になり、
  展開後に枝刈りをやり直す必要がないためである
  （OR前提があった頃は、選択肢として追加した項目が単独では予算に収まらない場合があり、
  展開の前後に1回ずつ枝刈りが必要だった）。

### 3.5 前提科目のハード制約担保 ★確定要件（issue #5 で実装済み）
前提科目制約は**ハード制約**であり、**QUBO の目的関数（ペナルティ項）には含めない**。

- AND前提: 子を選ぶなら親を**すべて**選ぶ（`z_child ≤ z_parent`）。**前提科目はこの1種類のみ。**

**担保機構**（実装: `calculation/prerequisites.py`）は次の3段階。

1. **候補集合の制限（前処理）**: 予算内で前提を満たせない項目を候補から除外する（第3.4節の予算枝刈り）。
2. **候補展開（前処理）**: 候補項目が必要とする前提科目を候補へ追加する。
3. **修復デコード（求解後）**: アニーリングの各サンプルを前提充足の選択に変換する。
   - **下方修復**（`repair_prerequisites`）: 前提未達の子項目を、すべて満たされるまで取り除く。
     AND制約は親の選択に対して単調なので、除去の順序によらず
     「元の選択に含まれる最大の実行可能部分集合」に収束する。
     項目を取り除くだけなので予算制約を新たに破ることはない。
   - **上方補完**（`complete_prerequisites`）: 前提が欠けていたサンプルには、
     不足親をすべて追加する補完も試す。予算に収まる場合のみ解の候補に加える。

   修復後の選択は**定義上すべて前提科目制約を満たす**ため、
   前提違反の解が最終候補に現れることは構造的にない。

子項目の価値は「前提が揃って初めて発生する条件付き価値」（第4節）として QUBO に残るが、
これは探索の誘導のみを担い、制約の担保には関与しない。

> 設計上の留意点への対応:
> - **予算制約との結合**: 予算検査は修復後の選択に対して行う。下方修復は時間を増やさず、
>   上方補完は予算超過なら候補にしないため、担保が予算と衝突しない。
> - **親の共有**: 前処理・デコードとも集合ベースの操作なので、コストの二重計上は起きない。
> - **循環の検査**: AND前提に循環があるとクロージャの計算が停止しないため、
>   `validate_prerequisite_data()` が起動時に循環を検査する。

### 3.6 時間の圧縮
QUBO 規模削減のため最大公約数で単位化する。

```
g   = gcd( T, { h_j : j ∈ C } )
c_j = h_j / g          （項目コスト）
B   = T / g            （予算）
```

## 4. 目的関数（QUBO）

決定変数 `z_j ∈ {0,1}`（j ∈ C）、スラック `s = Σ_k w_k y_k`（`y_k ∈ {0,1}`）。
最小化するエネルギー:

```
E(z) = − Σ_{j∈C, 前提なし} V_j · z_j                 … 線形項（項目価値の最大化）
       − Σ_{c∈C, 前提あり} G_c(z)                    … 条件付き価値（下記）
       − Σ_{i<j∈C} S_ij · z_i · z_j                 … 二次項（シナジー。S_ij < 0 の負相関も含む）
       + A · ( Σ_{j∈C} c_j · z_j + s − B )²         … 予算制約（スラック変数で等式化）
```

- **前提科目のペナルティ項・ORスラック変数（or_slack_*）は存在しない**（第3.5節の機構で担保）。
- **条件付き価値 G_c(z)**: 前提科目を持つ子 c の価値 `V_c` は線形項ではなく、
  「前提が揃って初めて発生する価値」として親との二次項で表現する。

  ```
  AND前提（親 p_1..p_n）: G_c = V_c · z_c · ( Σ_p z_p − (n−1) )
      全親を選択 → V_c（満額）／親が1つ欠ける → 0／さらに欠ける → 負（損）
  ```

  AND前提のみなので、この表現は近似ではなく「前提が揃ったとき、かつそのときだけ満額」を
  **厳密に**表す（OR前提があった頃は、選択肢数に比例させる近似項 `V_g/min(m,2)` が
  別に必要で、価値を2グループへ均等割りする処理も伴っていた）。

  係数は価値 V スケールであり、ペナルティ係数 A は使わない。
  条件付き価値は**探索の誘導のみ**を担い、前提充足の担保（第3.5節）には関与しない。
  そのためエネルギー地形が巨大な制約項に支配されない。
- スラック重み `w = bounded_binary_weights(B)`（`calculation/encoding.py`）で 0..B の整数を表現。
- ペナルティ係数（予算制約専用）

  ```
  A = max_j ( V_j + Σ_i max(0, S_ij) ) × ( 1 + penalty_margin )
      └─ 単一項目の限界寄与 ─┘         └ 既定 0.01（config/parameters.py）
  ```

  「違反を防ぐのに必要な最小値」から決める（issue #8）。予算を1単位超えた解からは、
  他の選択項目の前提になっていない項目（前提DAGの極大元。選択が空でなければ必ず存在する）を
  1つ除去すれば子の条件付き価値を巻き添えにせず実行可能化でき、そのとき失う報酬の主要項が
  単一項目の限界寄与 `V_j + Σ_i max(0, S_ij)` になる。`penalty_margin` は
  実行可能解と1単位違反解が同点になるのを避けるための微小マージン。

  旧式 `A = ( Σ_j max(0, V_j) + Σ_{S_ij>0} S_ij ) + 1 = 30.050` は「1単位の超過で
  全報酬が消える」ほど過大で、目的項の差 0.15〜2.4 に対し1〜2桁大きかった。
  現行は **A = 2.424** で目的項と同じ桁になっている。

  OR前提の廃止により、この限界寄与は**厳密な上界**になった。条件付き価値が AND のみと
  なり、親が揃ったときの子の報酬がちょうど `V_c`（満額）で頭打ちになるためである。
  したがって「`A >` 限界寄与 なら1単位違反の解は必ず実行可能解に負ける」と主張できる
  （OR前提があった頃は親を k 個選んだ子の報酬が `V_j · k / min(m,2)` まで膨らみ、
  限界寄与を上回りうるためこの保証がなかった）。

## 5. 求解（Solving）

- 既定サンプラー: `neal.SimulatedAnnealingSampler`
  （`num_reads=5000`, `num_sweeps=5000`, `seed=42`。`config/parameters.py`）。
- D-Wave QPU 等の外部サンプラーを注入可能
  （`recommend(..., sampler=..., sampler_kwargs=...)`）。
- **実機 QPU 実行**: `python main.py --backend qpu` で
  `EmbeddingComposite(DWaveSampler())` に切り替わる（`calculation/sampler.py`）。
  API トークンは `.env` の `DWAVE_API_TOKEN` から読む。
  既定は `num_reads=1000`, `annealing_time=20µs`, `answer_mode="raw"`
  （既定の `histogram` は同一サンプルを集約してしまい、neal とサンプル数を比較できないため）。
  鎖の強さは `uniform_torque_compensation` による自動決定。
- **実機での実測**（Advantage_system6, 適性 = `user_input.csv` の既定値, T=720h）
  ※ **OR前提の廃止前に測定した値**であり、再測定が必要（第8節）:
  34 変数の完全グラフ K34 が物理量子ビット 161〜173 個へ埋め込まれ
  （鎖長 平均 4.7〜5.1／最大 7）、QPU アクセス時間は 1000 リードで 0.13 秒。
  目的関数値は 15.6〜16.0 で、当時の厳密最適 18.650 に対する達成率は **84〜86%**
  （neal は 17.950／96.2%）。`num_reads` を 1000 → 5000 に増やしても改善せず、
  ボトルネックはサンプル数ではない。
  変数数・二次項数・ダイナミックレンジは OR 廃止後も変わらない（34 変数／二次項 561／896 倍）
  ため、埋め込みと鎖切れに関する所見はそのまま有効である。
  - **鎖切れ率が平均 9〜12%、鎖切れゼロのサンプルは 0.1% 未満**。
    多数決補正が入るため、実機のサンプルは論理 QUBO の解として信頼度が落ちる。
  - **QUBO 係数のダイナミックレンジが 896 倍**（予算制約ペナルティは
    重み 32 のスラック変数と掛かって数千、項目価値は 1 前後）。
    QPU は最大絶対値が 1 になるよう自動スケールしてから磁束を印加するので、
    項目価値の差が制御誤差（ICE）に埋もれる。倍精度で計算する neal では起きない。

## 6. 後処理・出力

- **修復デコード**: 各サンプルを下方修復（前提未達の子を除去）し、前提が欠けていた
  サンプルには上方補完（不足親の追加。予算内の場合のみ）も試す（第3.5節）。
  修復後の選択はすべて前提科目制約を満たすため、前提違反でサンプルが捨てられることはない。
- **実行可能解の抽出**: 修復後の選択に対して予算（`Σ h_j z_j ≤ T`）を検査し、
  **真の目的関数値** `Σ V_j z_j + Σ S_ij z_i z_j` が最大の解を採用する
  （同値なら合計時間が短い方）。QUBO エネルギーは修復前のビット列に対応する値であり、
  修復で項目が除かれると実際の価値とずれるため、順位付けには使わない。
  予算内の解が1つも無ければエラー。
- **最終検査**: `Σ h_j z_j ≤ T` および前提科目（`check_prerequisites`）の再確認。
- **出力**: テキストレポート（`output/report.py`）＋ グラフ（`output/visualize.py`）。

## 7. 確定した制約項の一覧（issue #1 表の更新版）

| 種別 | 目的 | 詳細 | 位置づけ |
| -- | -- | -- | -- |
| 線形項 V_i | 単体項目の価値最大化 | 適性相性 0.60 未満の分野は寄与を除外。前提を持たない項目のみ | QUBO 目的関数 |
| 条件付き価値 G_c | 前提充足時のみ子の価値を計上 | AND=全親で満額（近似なし）。係数は V スケール | QUBO 目的関数（探索誘導のみ） |
| 二次項 S_ij | シナジー（相乗効果） | 「Unity と Unreal Engine」等の負の相関も考慮 | QUBO 目的関数 |
| 予算制約 P_budget | 学習時間の上限 | スラック変数を導入し不等式を等式化。ペナルティ係数 A を使う唯一の制約 | QUBO 目的関数 |
| 分野相性フィルタ | 低相性分野・無価値項目の除外 | 相性 0.60 未満の分野寄与を 0、価値0項目を候補外に | 前処理 |
| 予算枝刈り | 予算内で前提を満たせない項目の除外 | minClosureHours(j) > T の項目を候補外に | 前処理 |
| 前提科目（AND） | 依存関係の担保 | 親を全て選ぶ。ハード制約。ペナルティ項・ORスラックは廃止 | **前処理＋修復デコード**（★実装済み） |
| 学習済み除外 | 既習項目を推薦しない | L の項目を候補から外し、実効前提 `P'` と実効価値 `V'` へ畳み込む | **前処理**（第10節・★実装済み） |

- **流行項（人気・トレンド）**: 別issueで検討する。データ源・スコア化・線形項としての組み込み方は未定。
  （issue #1 コメント「流行項を追加するかも」）。
- **OR前提が担っていた弱い依存の再表現**: OR前提の廃止により、
  「Git を選ぶなら言語を1つ以上やっていること」といった弱い依存は**どこにも表現されていない**。
  結果として、モバイル言語を1つも選ばずに `モバイルUI` を選ぶ解などが実行可能になっている
  （第9節）。必要ならシナジー `S_ij` として入れ直すか、必須性の高いものは AND 前提へ移す。
- **実機 QPU の再測定**: 第5節の QPU 実測は OR 前提の廃止前の値であり、
  厳密最適解が 18.650 → 18.850 に変わったため達成率の分母が変わっている。
- **予算 T が最小項目に届かないケース**: r2 の回答は T = 4h × 4週 = 16h で、
  最安の項目（`開発環境/ターミナル` 20h）すら買えず候補が0件になり `RuntimeError` で
  落ちる。学習済み除外（第10節）でも解決しない。エラーメッセージの改善に留めるか、
  部分学習・最小コスト項目の提示といったフォールバックを設けるかは別 issue とする。

## 9. OR前提の廃止（本改訂）

前提科目のうち **OR前提（`z_child ≤ Σ z_parents`、8件）を廃止**し、AND前提のみとした。

**廃止した OR 関係**

| 子項目 | 選択肢だった親 |
| -- | -- |
| SQL/データベース | バックエンド言語 / Python基礎 |
| アルゴリズム | バックエンド言語 / Python基礎 / C# / C++ |
| モバイルUI | Swift/Kotlin / Flutter/RN |
| アプリ設計 | Swift/Kotlin / Flutter/RN |
| ゲーム数学・物理 | C# / C++（AND前提「アルゴリズム」は残る） |
| 3Dグラフィックス | C# / C++（別途 AND前提「ゲーム数学・物理」を追加。第11節） |
| Git | JavaScript/TS / バックエンド言語 / Swift/Kotlin / Flutter/RN / Python基礎<br>（別途 AND前提「開発環境/ターミナル」を追加。第11節） |
| 開発環境/ターミナル | JavaScript/TS / バックエンド言語 / Swift/Kotlin / Flutter/RN |

**廃止の理由**

1. これらは「必ず必要」ではなく「あると効く」弱い依存であり、
   本来はハード制約ではなくシナジー `S_ij` で表すべき関係だった。
2. 条件付き価値の分母 `min(m,2)` が近似でしかなく、探索の誘導が偏っていた（旧第8節）。
3. 予算枝刈り・修復デコードの分岐処理の大半が OR 側にあった。

**モデルへの影響**

| | OR 廃止前 | OR 廃止後 |
| -- | -- | -- |
| 条件付き価値 | AND は厳密／OR は近似 | **すべて厳密**（近似項なし） |
| ペナルティ係数 A の根拠 | 限界寄与は厳密な上界ではない | **厳密な上界**（第4節） |
| 予算枝刈り | 候補展開の前後に2回 | **前に1回**（第3.4節） |
| 前提クロージャ | 選択肢ごとに分岐して最小値を探索 | **一意に定まる**（第3.4節） |
| QUBO 規模 | 34変数 / 二次項 561 | **変化なし**（34変数 / 二次項 561） |

QUBO 規模が変わらないのは、予算制約のペナルティ項が全変数ペアに二次項を張るため、
OR 由来の二次項を除いてもペアの**本数**は変わらず係数だけが変わるからである。

**副作用（要注意）**: OR前提が禁じていた選択が実行可能になった。
デモ条件の厳密最適解は `モバイルUI` を Swift/Kotlin・Flutter/RN のどちらも選ばずに含む。
「モバイル言語を学ばずにモバイルUIを学ぶ」学習計画は推薦として不自然であり、
第8節のとおり再表現の要否を検討する必要がある。

## 10. 学習済み科目の除外 ★確定要件（実装済み）

アンケート設問「下記のリストの中にすでに学習を終えた科目があれば、チェックしてください」の
回答を入力に加え、**学習済み項目は推薦しない**。回答は現在 `user_input_r1..r5.csv` の
コメント内に控えとして書かれているだけで、パーサは読んでいない。

> **データ前提の確認**: r1〜r5 の学習済み科目 計35件は**すべて `config/items.py` の
> 項目名と完全一致**する（表記ゆれゼロ）。アンケートのチェックリストが項目定義から
> 作られているためであり、名前の正規化・あいまい一致は不要である。

### 10.1 原理：学習済み＝「z=1 に固定した変数」

学習済み集合 **L ⊆ items** を「決定変数 `z_j = 1` に固定して QUBO から消した項目」とみなす。
前提・シナジー・候補集合の扱いはすべてこの一点から導く。
ただし本モデルの時間と価値は「**これから**学ぶ分」だけを数えるため、
通常の変数固定と次の2点だけ異なる。

| | 通常の変数固定 | 本仕様 |
| -- | -- | -- |
| 時間 | 固定分 `Σ_{j∈L} h_j` を予算から差し引く | **差し引かない**（過去に消費済み。T は今後の予算） |
| 価値 | 固定分 `Σ_{j∈L} V_j` を定数項として加算 | **加算しない**（目的関数値＝これから得る価値） |

したがって L の項目は QUBO の変数にもならず、予算式にも目的関数にも現れない。
残るのは **前提の解放** と **シナジーの畳み込み** の2つの効果だけである。

### 10.2 入力形式（`inputs/data/user_input*.csv`）

```
key,value
クリエイティブ,0.0
...
hours_per_week,4
weeks,4
learned,"HTML/CSS, Python基礎, 統計・数学, Unity"
```

- `learned` キーは**省略可**。キーが無い／値が空＝ `L = ∅`。既存の CSV はそのまま動く。
- 値はカンマ区切りの項目名。CSV の仕様上ダブルクォートで囲む。
  フォーム回答セルをそのまま貼り付けられる形にしてある。
- 各要素は前後の空白を除去する。空要素は無視。重複は1つに畳む（エラーにしない）。
- **`config/items.py` に存在しない項目名は `ValueError`** で停止する。
  表記ゆれを黙って捨てると「除外したつもりが除外されていない」事故になるため、
  fail fast にする。
- `learned` は `_read_key_values` の既知キー（`unknown` 判定）へ追加する。

### 10.3 実効前提 `P'`

学習済みの親は**すでに満たされている**とみなし、前提辞書を実行時に畳む。

```
P'(c) = P(c) \ L        （c ∉ L）
P' の定義域から L の項目自身も除く（子としても親としても現れない）
```

- `P'(c) = ∅` になった子は「**前提のない項目**」として扱う。
  価値は条件付き二次項ではなく線形項へ戻る（第4節の分岐は `P'` で判定する）。
- 前提クロージャも `P'` で計算する。L の項目はクロージャに含まれない。

  ```
  closure'(j) = {j} ∪ ⋃_{p ∈ P'(j)} closure'(p)
  minClosureHours'(j) = Σ_{n ∈ closure'(j)} h_n
  ```

- `config/prerequisites.py` の `and_prerequisites` は**書き換えない**。
  `P'` は前処理で作る実行時の辞書であり、係数データは不変に保つ。

**学習済み集合が前提を満たしていない場合（自己申告の不整合）**

実データに2件ある（r2「Unity 済 / C# 未」、r3「機械学習 済 / 統計・数学 未」）。

- **自己申告を尊重し、警告を1行出して続行する。** 学習済みは「その項目自身」だけを
  満たし、前提へは伝播しない。上の例では C# ・統計・数学 は候補に残り、
  価値があれば推薦されうる。
- クロージャを自動補完して学習済み扱いにはしない（学んでいない科目を
  「学習済み」と断定して永久に推薦対象から外すのは、除外の副作用として重すぎる）。
- エラーで停止もしない（実データ2件が現状のまま動かせなくなる）。

### 10.4 候補集合（第3.4節の差分）

```
C = ( { j : V_j > 0 } \ L )
      → 予算枝刈り（minClosureHours'(j) > T を除外）
      → 実効前提 P' で候補展開（追加される親も L には属さない）
```

- **候補入りの判定には元の分野価値 `V_j > 0` を使う**（実効価値 `V'_j` ではない）。
  学習済みシナジーのボーナスだけで、相性0.60未満の分野の項目が候補に
  紛れ込むのを防ぐため（例：QA分野の相性が0の人に、既習 Git とのシナジー +0.15
  だけを理由に `テスト自動化` を推薦してしまう、という事故を避ける）。
- 枝刈りを候補展開の**前に1回だけ**行ってよい根拠は L ≠ ∅ でも変わらない。
  `closure'(parent) ⊆ closure'(child)` は L を除いても成り立つためである。
- 学習済みの除外は候補を**減らすとは限らない**。前提が解放されてクロージャ時間が
  縮み、これまで枝刈りされていた項目が予算内に入ることがある
  （実測 r3: T=72h で 13件 → 15件）。
- `C = ∅` はこれまで通り `RuntimeError`。ただしメッセージに予算 T と
  最小クロージャ時間を含め、「予算不足」か「学習済みで尽きた」かを区別できるようにする。

### 10.5 目的関数（第4節の差分）

**学習済みシナジーの畳み込み**：`z_i = 1 (i ∈ L)` を代入すると、二次項 `S_ij z_i z_j` は
`S_ij z_j` すなわち項目 j の線形ボーナスに落ちる。これを項目価値へ畳み込む。

```
B_j  = Σ_{i ∈ L} S_ij            （学習済みシナジーの合計。負にもなりうる）
V'_j = V_j + B_j                 （実効価値。j ∈ C）
```

- 正負ともに畳み込む。負のシナジー（`Unity × Unreal Engine = −0.5` 等）は
  「同時学習の非効率」であると同時に「重複スキルの冗長性」でもあり、
  既習との関係でも成立するとみなす。
- `V'_j` は QUBO 係数と目的関数値にのみ使う。候補判定は 10.4 のとおり `V_j`。

**第4節の目的関数は、`V_j` をすべて `V'_j` に置き換えるだけで済む。**

```
E(z) = − Σ_{j∈C, P'(j)=∅} V'_j · z_j
       − Σ_{c∈C, P'(c)≠∅} V'_c · z_c · ( Σ_{p∈P'(c)} z_p − (n'−1) )     n' = |P'(c)|
       − Σ_{i<j∈C} S_ij · z_i · z_j
       + A · ( Σ_{j∈C} c_j · z_j + s − B )²
```

- 前提を持つ子については、ボーナス `B_c` も**条件付き価値の側に含める**
  （`V'_c` ごと二次項にする）。`B_c` だけを無条件の線形項にすると、
  前提未達のまま子を立てるとボーナスだけ得られる形になり、探索の誘導が濁るため。
  「前提が揃って初めて満額 `V'_c`」という第4節の性質はそのまま保たれる。
- `V'_j = 0` の項目に誘導項を付けない現行の分岐は、`V_j == 0` ではなく
  `V'_j == 0` で判定する。
- 予算式に L は現れない（時間を消費しない）。

**真の目的関数値**（修復デコード後の順位付け・`best_score`）も同じ置き換えを行う。

```
score(z) = Σ_{j∈C} V'_j z_j + Σ_{i<j∈C} S_ij z_i z_j
```

### 10.6 ペナルティ係数 A（第4節の差分）

限界寄与の定義で `V_j` を `V'_j` に置き換える。根拠（1単位超過解からは前提DAGの
極大元を1つ除去すれば実行可能化でき、そのとき失う報酬の主要項が限界寄与）は不変。

```
A = max_{j∈C} ( max(0, V'_j) + Σ_{i∈C} max(0, S_ij) ) × ( 1 + penalty_margin )
```

- 学習済みシナジー `B_j` は「項目 j を1つ追加したときに解放される報酬」に含まれるため、
  `V'_j` を使わないと A が過小になり、1単位違反解が実行可能解に勝ちうる。
- 内側の和 `Σ_{i∈C}` は候補内のペアのみ（L との分は `V'_j` 側に入っているので
  二重計上しない）。

### 10.7 修復デコード・最終検査（第3.5節・第6節の差分）

- 下方修復・上方補完・`check_prerequisites` はいずれも `P'` を見る。
  L の項目は `z` 上では常に 0 のままであり、前提違反として扱われない。
- 予算検査は従来どおり `Σ_{j∈C} h_j z_j ≤ T`。L の時間は入らない。

### 10.8 出力（第6節の差分）

- **【学習済みとして除外】** 項目名（時間）の一覧と合計時間を表示する
  （実測: r2=340h / r3=590h / r4=390h / r5=140h と、節約時間は予算に対して大きい）。
- 推薦項目のうち、前提が既習で満たされたものには
  「前提〇〇は学習済み」の注記を付ける。
- `B_j ≠ 0` の項目には「既習シナジー: Python基礎(+0.40)」のように内訳を出す。
- 10.3 の不整合（学習済みの前提が未習）は警告として1行出す。

### 10.9 検証ツールの同期

`tools/exact_bb.py` は本体と同じ候補集合・価値・前提で厳密最適解を出す前提なので、
`P'` と `V'` を同じく使うよう追随させる。追随しないと達成率の比較が無意味になる。

### 10.10 実装箇所

| ファイル | 役割 |

| `inputs/user_input.py` | `learned` キーのパースと項目名の検査（`_parse_learned`） |

  今回はエラーメッセージの改善のみとし、フォールバック設計は別 issue とする。

## 11. 必須性の高い依存の AND 前提への追加（本改訂）

第9節で OR 前提を廃止した際、第8節に「必須性の高いものは AND 前提へ移す」と残していた
宿題を処理する。AND は全親必須なので、**親が一意に定まる依存だけ**を追加した。
依存は 17 → 23 本、前提を持つ子項目は 15 → 20 件になる
（`テスト自動化` は既に `Python基礎` を前提に持っていたため、子項目としては新規ではない）。

| 追加した AND 前提 | 根拠 | minClosureHours |
| -- | -- | -- |
| WordPress ← HTML/CSS | テーマ編集・カスタマイズは HTML/CSS なしに成立しない | 40h → 80h |
| SEO/サイト運営 ← HTML/CSS | オンページ SEO は meta / 構造化データの理解が前提 | 30h → 70h |
| 画像編集 ← デザインツール(PS/AI) | 編集ツールなしに画像編集の工程が存在しない | 30h → 70h |
| 3Dグラフィックス ← ゲーム数学・物理 | 座標変換・ベクトル・行列が前提。既存の `ゲーム数学・物理 ← アルゴリズム` に連結する | 80h → 240h |
| Git ← 開発環境/ターミナル | Git は CLI ツールであり、ターミナル操作が前提 | 30h → 50h |
| テスト自動化 ← テスト技法(JSTQB) | 自動化の対象は設計済みのテストケース。技法なしの自動化は成立しない | 130h → 170h |

**OR 前提との関係**

3Dグラフィックスと Git は第9節で OR 前提を廃止した子項目だが、ここで追加した親は
廃止した選択肢とは別物である。「言語のうちいずれか」は AND にできないのに対し、
「ゲーム数学・物理」「開発環境/ターミナル」は選択の余地がないため AND として書ける。

**追加しなかったもの**

| 見送った依存 | 理由 |
| -- | -- |
| SQL/データベース、アルゴリズム、モバイルUI、アプリ設計 | 親が選択制。AND にすると「Swift/Kotlin と Flutter/RN を両方必須」のような誤った制約になる。第9節のとおりシナジー側の扱いとする |
| UI/UXデザイン ← デザイン基礎 | 依存自体は妥当だが、UI/UXデザイン分野 → グラフィックデザイン分野への越境になり、UI/UX を選ぶたびに他分野の項目が強制されて `field_score` が歪む |
| 全プログラミング項目 ← 開発環境/ターミナル（7件） | 意味的には正しいが、17項目の minClosureHours が一律 +20h され、20h が実質的な固定費になる。探索空間が縮むだけで表現力は上がらない |

**モデルへの影響**

- 最大クロージャは 350h（機械学習）のまま変わらない。
- 既定の `T = 720h` では予算枝刈りの結果は変化しない（除外0件）。
  `T ≤ 200h` の低予算時にのみ 3Dグラフィックス（240h）が新たに候補から外れる。
- 前提を持つ子項目は 15 → 20 件になり、第4節の条件付き価値 `G_c` の対象がその分増える。
  `テスト自動化` は親が1 → 2に増えるため `G_c = V_c · z_c · (Σ_p z_p − 1)` の形になる。
- 追加した子項目はいずれも他項目の親ではないため、前提グラフに循環は生じない
  （`validate_prerequisite_data` で検査済み）。

**シナジーとの重複（未処理）**

`config/synergy.py` の以下2ペアは、対応する AND 前提が既に存在するため
「子を選べば必ず両方選ばれる」状態にあり、二次項としてのシナジーが
子項目への線形ボーナスに退化している。

| シナジーペア | 対応する AND 前提 |
| -- | -- |
| (JavaScript/TS, フロントFW(React等)) = 0.2 | フロントFW(React等) ← JavaScript/TS |
| (Python基礎, 統計・数学) = 0.4 | 統計・数学 ← Python基礎 |

ペア効果を意図しているなら削除して `item_value` 側へ寄せるべきだが、
係数の再調整を伴うため本改訂のスコープ外とする。

# プレゼン資料：盛り込む内容

IT学習項目推薦システムの発表用メモ。
主題は **「実問題を QUBO へ落とし込む定式化」＋「前提科目を前処理でハード制約として担保する設計」**。
解の品質は現状の課題として率直に提示する。

> - 係数（分野プロファイル・シナジー値・最低相性 0.60）は**仮の値**であり、
>   根拠データに基づく調整は今後の課題（issue #12）。
>   ペナルティ係数だけは限界寄与基準で導出済み（4.7、issue #8）。
> - **前提科目の扱い**：「前処理でハード制約として担保（目的関数に含めない）」で
>   **実装済み**（要件定義 §3.5、issue #5）。ペナルティ項方式との比較は経緯として 4.8 に残す。

---

## 1. 課題設定

**「限られた学習時間で、何をどの順に学べば最も効果的か」** を決めたい。

- IT分野は多岐にわたり、初学者が独力で学習計画を立てるのは難しい
- 単に「価値の高い項目を並べる」だけでは駄目な理由が3つある
  1. **時間予算**がある（週30h × 24週 = 720h など）
  2. **前提科目**がある（Unity を学ぶには C# が要る／機械学習には Python と統計が要る）
  3. **組み合わせ効果**がある（Docker と AWS は相乗／Unity と Unreal Engine は非効率）

→ 個々の項目を独立に評価できない **組合せ最適化問題**。

---

## 2. なぜ QUBO なのか

| 要素 | 表現 | 置き場所 |
| --- | --- | --- |
| 項目単体の価値 | 線形項 | QUBO 目的関数 |
| 組み合わせ効果（シナジー） | **二次項** | QUBO 目的関数 |
| 時間予算 | ペナルティ項（ソフト制約） | QUBO 目的関数 |
| **前提科目** | **ハード制約** | **前処理**（★確定方針） |

特に **負のシナジー**（同時に学ぶと非効率）は、項目を独立に評価する
線形モデルでは原理的に表現できない。二次項を持つ QUBO の必然性がここにある。

一方、**前提科目は「破ってよい度合い」が存在しない論理制約**なので、
ペナルティで抑え込むのではなく前処理で構造的に保証する（第4.2節）。
「何をペナルティにし、何をペナルティにしないか」の切り分け自体が設計判断である。

## 3. システム全体像

```
適性5軸ベクトル u（ユーザー入力）
  ↓  平均二乗距離
各IT分野との相性 fs（10分野）
  ↓  閾値 0.60 未満を除外
分野関連度 fr
  ↓  所属分野の関連度を合計
学習項目価値 V(u)（39項目）
  ↓  価値0の項目を除外＋前提科目クロージャ
候補集合 C(u)（27項目）
  ↓  前提科目の担保（前処理・ハード制約）★確定方針
  ↓  予算・シナジーのみを QUBO 化（34変数・試算）
シミュレーテッド・アニーリング
  ↓
実行可能解の抽出 → 推薦結果
```

※ 旧実装では前提科目も QUBO 内のペナルティ項だった（53変数）。第4.8節参照。

**構成**（Python / dimod / neal）

| ディレクトリ | 役割 |
| --- | --- |
| `config/` | 係数・データ定義（分野・項目・シナジー・前提科目） |
| `inputs/` | ユーザー入力（CSV で適性と学習時間を指定） |
| `calculation/` | QUBO 構築・アニーリング |
| `output/` | テキストレポート・グラフ3枚 |

データと計算ロジックを分離してあるため、**係数の差し替えだけでモデルを調整できる**。

## 4. 定式化 ★発表の中心

### 4.1 適性はどこに入るか ★頻出質問への先回り

ハミルトニアン（4.4）だけを見ると適性 u が現れないが、
**u は前処理で線形係数 V と候補集合 C に畳み込まれている**。

```
fs_f(u) = clip( 1 − (1/5) Σ_a (F_{f,a} − u_a)² , 0, 1 )   … 分野相性（完全一致=1）
fr_f(u) = fs_f  (fs_f ≥ 0.60) / 0  (fs_f < 0.60)          … 低相性分野の足切り
V_j(u)  = Σ_{f ∈ fields(j)} fr_f(u)                        … 項目価値
```

**適性 → 分野相性 → 項目価値** と伝播し、線形項の係数として効く。

例）u = [1.0, 1.0, 1.0, 0.5, 1.0] のとき、SQL/データベース（2分野に所属）は

| 所属分野 | プロファイル F_f | 相性 fs_f |
| --- | --- | --- |
| バックエンド | [0.0, 1.0, 1.0, 0.5, 1.0] | 0.800 |
| データ/ML | [0.0, 1.0, 0.5, 1.0, 0.5] | 0.650 |

→ V_SQL = 0.800 + 0.650 = **1.450**

**何がユーザー依存で、何が共通か**

| | 適性 u への依存 |
| --- | --- |
| 線形係数 V_j(u) | **依存する**（ユーザーごとに変わる） |
| **候補集合 C(u)** | **依存する**（V=0 の項目は候補外。39項目 → 27項目） |
| 二次係数 S_ij | 依存しない（全ユーザー共通） |
| 予算制約 | 依存しない |
| 前提科目 | 依存しない |

適性は係数だけでなく**問題サイズそのものを変える**。
逆に、この設計では適性が「組み合わせの好み」には影響しない
（誰にとっても Docker × AWS は +0.3）。S_ij(u) への拡張は将来の論点。

### 4.2 前提科目のハード制約担保 ★設計の主役

**方針（確定）**：前提科目は QUBO の目的関数（ペナルティ項）に**含めず**、
前処理段階でハード制約として保証する。

- AND前提：子を選ぶなら親を**すべて**選ぶ（z_child ≤ z_parent）
- OR前提：子を選ぶなら選択肢のうち**少なくとも1つ**を選ぶ（z_child ≤ Σ z_parents）

**なぜペナルティにしないか（実測に基づく判断）**

旧実装（ペナルティ方式）の 5000 サンプルの内訳：

| 判定 | 件数 | 割合 |
| --- | --- | --- |
| **前提科目違反** | **4168** | **83%** |
| スラック等式違反 | 207 | 4% |
| 予算違反 | 25 | 1% |
| 実行可能 | 797 | 16% |

**サンプルの83%が前提科目違反**で捨てられており、探索の大半が無駄になっている。
前提科目を構造的に保証すれば、この違反カテゴリは**定義上ゼロ**になる。

**QUBO 規模への効果（デモ条件・実測）**

| | 変数 | 二次項 |
| --- | --- | --- |
| 旧実装（前提科目＝ペナルティ項） | 53 | 653 |
| 前処理化後（現行） | **34**（−36%） | **561**（−14%） |

内訳：AND/OR ペナルティに使っていた OR スラック19変数が丸ごと消える。

**担保機構の候補（実装issueで詳細設計）**

| 候補 | 概要 | 課題 |
| --- | --- | --- |
| バンドル化 | 子と前提の連鎖を1変数に束ねる | OR の選択自由度が失われる／親を共有する場合の重複 |
| 変数消去（含意の構造化） | 子の変数を「親との積」に置換し含意を構造的に保証 | 次数が上がり QUBO 化に再変換が必要 |
| 候補集合の制限 | 前提を賄えない項目を事前に候補から外す | 予算との結合で「賄えるか」が事前に確定しない |

**共通の難所**：前提科目は予算制約と結合する（子を選ぶと親の hours も消費する）ため、
単純な事前確定はできない。OR前提の選択自由度、親の共有も考慮が要る。
→ 機構の比較検討と実装は次の issue（8.2）。

### 4.3 決定変数

```
z_j ∈ {0,1}   (j ∈ C(u))   … 学習項目 j を学習計画に含めるか、含めないか
```

（一般には x_i と書かれることが多いが、本資料はコードに合わせ z とする）

**添字は 1 つだけ**。決めているのは「どの項目を学ぶか」という**集合**であり、
学習の順序・時期は決めていない。前提科目も順序制約ではなく**集合の包含関係**
（z_Unity ≤ z_C# は「C# を先に学ぶ」ではなく「C# も選ぶ」の意）。

厳密には **前提科目つき・シナジーつきのナップサック問題**であって、スケジューリング問題ではない。
（時間軸を持つ定式化への拡張は第8.1節）

これに加えて、予算不等式を等式化する**スラック変数**が入る（解の意味を持たない計算上の道具）。

| 変数 | 意味 | 個数（目標設計） |
| --- | --- | --- |
| `item_j` = z_j | 項目 j を学ぶか | 27 |
| `slack_k` | 予算の余り時間のバイナリ展開・第 k 桁 | 7 |
| | **合計** | **34** |

※ 旧実装ではさらに OR 前提用スラック 19 変数が加わり 53 変数だった（第4.8節）。

### 4.4 目的関数（ハミルトニアン）

```
H(z) = − Σ_{j∈C(u)} V_j(u) z_j          … 線形項（項目価値。適性はここに入る）
       − Σ_{i<j} S_ij z_i z_j            … 二次項（シナジー。負値も可）
       + A ( Σ_j c_j z_j + s − B )²      … 予算制約（スラックで等式化）
```

- **前提科目のペナルティ項は含めない**（4.2 の前処理で担保。★確定方針）
- 二次項は i<j で走る（S は対称行列なので Σ_{i,j} と書くと二重計上になる）

### 4.5 予算制約：不等式 → 等式変換

QUBO は等式制約しか自然に表せないため、**スラック変数**を導入する。

```
Σ c_j z_j ≤ B    →    Σ c_j z_j + s = B    →    A ( Σ c_j z_j + s − B )²
```

`s` は `bounded_binary_weights(B)` によるバイナリ展開。
B = 72 に対し重み **[1, 2, 4, 8, 16, 32, 9]** の7変数で 0〜72 を過不足なく表現。
（単純な 2 冪だと 0〜127 まで表せてしまい無駄が出る。上限で打ち切るのが工夫点）

### 4.6 変数削減：最大公約数による時間圧縮

予算と候補項目の学習時間の GCD で単位化する。

```
g = gcd(720, {40, 90, 60, ...}) = 10
→ 720h = 72単位、40h = 4単位
```

スラック変数は **10個 → 7個** に削減される（実測値）。

```
B=720（圧縮なし）: [1, 2, 4, 8, 16, 32, 64, 128, 256, 209] … 10変数
B=72 （GCD圧縮）: [1, 2, 4, 8, 16, 32, 9]                  …  7変数
```

バイナリ展開なので変数数は log オーダーであり削減幅自体は 3 変数だが、
**ペナルティ項の係数の桁が 2 桁下がる**効果のほうが大きい
（予算制約の二次項は係数の積で効くため、数値的な安定性に直結する）。

### 4.7 ペナルティ係数

```
A = max_j ( V_j + Σ_i max(0, S_ij) ) × 1.01 = 2.400 × 1.01 = 2.424
      └─ 単一項目の限界寄与 ─┘
```

「**違反を防ぐのに必要な最小値**」から決める。予算を1単位超えた解からは、他の選択項目の
前提になっていない項目を1つ除去すれば実行可能化でき、そのとき失う報酬の主要項が
単一項目の限界寄与だからである（×1.01 は同点を避ける微小マージン）。

旧設計は `A = 報酬上限 + 1 = 30.050`（「いかなる制約違反も最大報酬を上回る損失」）で、
目的項の差 0.15〜2.4 に対し**1〜2桁大きかった**。現行は目的項と同じ桁に収まっている。

**※ ただし桁差の解消は解の品質を改善しなかった（第7.1節）。**

### 4.8 旧実装との差分（経緯として簡潔に）

旧実装では AND/OR 前提もペナルティ項として QUBO 化していた
（AND は `A·z_child(1−z_parent)` の2項、OR は予算と同じスラック法で二乗ペナルティ化）。
**QUBO 化自体は実装・検証済み**だが、実測で**サンプルの83%が前提違反**となり
探索効率を大きく損なうことが分かったため、**前処理でのハード制約担保へ移行した**（4.2、issue #5）。

→ 「まず全部 QUBO に入れて動かし、実測に基づいて制約の置き場所を仕分けた」という
**設計判断の物語**として1枚で話す。

## 5. 実装上の工夫：修復デコードと実行可能解の抽出

アニーリングの**最低エネルギー解をそのまま採用してはいけない**。低エネルギー側にも制約違反解が混ざる。
現行実装は各サンプルを**修復デコード**してから採用候補にする。

1. **下方修復**：前提が欠けている子項目を取り除く（項目が減るだけなので予算を新たに破らない）
2. **上方補完**：代わりに不足している親を足す解も試し、予算内なら候補に加える
   （高価値の子項目を捨てずに済む解を拾うため）
3. 修復後の選択に対して予算 `Σ h_j z_j ≤ T` を検査する

修復後の選択は定義上すべて前提を満たすため、**前提違反を理由にサンプルが捨てられることはない**。
残る検査は予算のみになる。

順位付けは**QUBOエネルギーではなく、修復後の真の目的関数値** `Σ V_j z_j + Σ S_ij z_i z_j` で行う。
エネルギーは修復前のビット列に対応する値であり、修復で項目が除かれると実際の価値とずれるため。
さらに採用後、予算と前提科目を**再検査**する二重の安全機構を設けた。

**効果**：旧実装（ペナルティ方式）では実行可能解が 5000中 **797件（16%）** だったのに対し、
現行実装では **5000中 4994件（99.9%）**。83%を占めていた前提違反が構造的に消えた。
ただし第7章のとおり、この改善は**解の品質の改善には直結していない**。

→ グラフ3枚目（エネルギー分布・実行可能／違反を色分け）がこの機構を可視化している。

## 6. デモ結果（現行実装での実測）

**入力**：クリエイティブ 1.0 / ロジカル 1.0 / 作る↔運用 1.0 / 数学 0.5 / 計画性・正確さ 1.0、週30h × 24週 = 720h

**分野相性**（0.60 以上を採用）

| 採用 | 除外 |
| --- | --- |
| UI/UXデザイン 0.850、フロントエンド 0.800、バックエンド 0.800、モバイルアプリ 0.800、ゲーム開発 0.700、データ/ML 0.650 | グラフィックデザイン 0.550、インフラ/クラウド 0.550、Webサイト管理 0.500、QA・テスト 0.500 |

**推薦結果（13項目 / 720h ちょうど / 目的関数値 17.950。既定シード 42）**

開発環境/ターミナル(20h)、Git(30h)、アルゴリズム(100h)、HTML/CSS(40h)、API設計(50h)、
SQL/データベース(40h)、デザインツール Figma(30h)、UI/UXデザイン(50h)、Firebase/Supabase(40h)、
フロントFW React等(60h)、バックエンド言語(80h)、JavaScript/TS(90h)、C#(90h)

**定式化が意図通り働いた証拠**

- **複数分野で使える項目が上位**：開発環境/ターミナルと Git が価値 2.400 で最上位
  （フロントエンド・バックエンド・モバイルの3分野に効く）
- **前提科目が自動で確保された**：フロントFW を選んだ結果 JavaScript/TS → HTML/CSS が連鎖して選択。
  API設計・Firebase/Supabase を選んだ結果 バックエンド言語 が確保され、
  SQL・アルゴリズム・Git の OR 前提も同時に満たされている（**親の共有**）
- **シナジーが働いた**：HTML/CSS × Figma (+0.30)、JS/TS × React (+0.20)、React × UI/UX (+0.20)
- **負のシナジーのペアは共存していない**：Unity × Unreal Engine (−0.50)、
  Swift/Kotlin × Flutter/RN (−0.20) はいずれも同時選択されていない
  （ただしこの解では両ペアとも非選択なので、排他性の証拠としては弱い）

**一方で最適ではない**：C#(90h) は価値 0.700 しかなく、この 90h をモバイル分野の
応用項目へ回した方が目的関数値は高くなる（第7章）。

## 7. 現状の課題 ★誠実に提示する

厳密解（分枝限定法）と比較して、**解の品質に差**があることが分かった。

| 手法 | 目的関数値 | 達成率 | 計算時間 |
| --- | --- | --- | --- |
| 厳密最適解（分枝限定法） | **18.650** | 100% | **1.8s** |
| 貪欲法（価値密度 V/h 順） | 18.650 | 100% | 即時 |
| **QUBO + SA（neal・現行既定）** | **17.638** | **94.6%** | 約34s |
| **QUBO + 実機 QPU（Advantage_system6）** | **14.000** | **75.1%** | QPU 0.13s |

（比較の測定スクリプトは `tools/exact_bb.py` としてリポジトリに収録。検証専用ツールであり、
QUBO本体の calculation/ からは参照されない。アニーリングの値は **12シード平均**
（42, 1, 7, 123, 2024, 3, 11, 99, 256, 777, 1234, 31337）。単一シードでは 17.100〜18.000 と
ばらつき、たまたま最適解と一致するシードもあるため、**単一シードの値で比較してはいけない**）

- **最適解との差**：最適解は Flutter/RN(80h) 経由でモバイル分野を応用項目まで積み上げる
  （モバイルUI・アプリ設計・アプリストア公開）のに対し、アニーリング解は
  JavaScript/TS(90h)・C#(90h)・フロントFW(60h) 等の高コスト基礎項目に費やし、応用項目に到達できていない
- 最適解は 30h を余らせる。**予算を使い切る解が最良とは限らない**

### 7.1 検証したが外れた仮説：ペナルティ係数の桁差（issue #8）

当初の見立てはこうだった——「ペナルティ係数 `A = 30.050` に対し目的項の差はわずか 0.15〜2.4。
**制約項が目的項より1〜2桁大きく**、エネルギー地形が制約充足に支配されて、
実行可能解どうしの優劣をアニーラーがほとんど識別できていない」。

そこで A を「違反を防ぐのに必要な最小値」（単一項目の限界寄与基準、4.7）へ下げ、
30.050 → 2.424 と**桁差を解消した上で再測定した**。

| A | 42 | 1 | 7 | 123 | 2024 | 5シード平均達成率 |
| --- | --- | --- | --- | --- | --- | --- |
| 30.050（旧・報酬上限+1） | 18.650 | 17.000 | 17.700 | 17.250 | 17.350 | **94.3%** |
| 2.424（新・限界寄与×1.01） | 17.950 | 18.000 | 17.100 | 17.800 | 17.650 | **94.9%** |

さらに `penalty_margin` を振って A を 2.4〜29.8 の範囲で連続的に変えても、
達成率は 91.6〜95.8% の間で**単調な傾向を示さない**（＝シード間ばらつきに埋もれる）。

> **結論：桁差は解の品質のボトルネックではなかった。**
> 「制約項が大きすぎて実行可能解どうしの優劣を識別できない」という見立ては、実測で支持されなかった。
> A の適正化そのものは数値的な健全性（二次項の係数の積が小さくなる）として意味があるが、
> **品質改善の手段ではない**。

品質差の原因は別にあると考えられる。候補は (a) 条件付き価値による OR 前提の近似、
(b) 修復デコードが探索空間と真の目的関数の対応をずらしていること、
(c) そもそも SA がこの規模のナップサック型問題を苦手とすること。切り分けは未着手。

### 7.2 実機 D-Wave QPU での実測（Advantage_system6）

`python main.py --backend qpu` で同じ QUBO を実機へ投げた。**動くことは確認できたが、
品質は neal を大きく下回った**（4回平均 14.000／達成率 75.1%、単発では 12.650〜15.950）。
`num_reads` を 1000 → 5000 に増やしても 15.600 で、**サンプル数はボトルネックではない**。

| 指標 | 実測値 |
| --- | --- |
| 埋め込み | 34 変数の完全グラフ K34 → 物理量子ビット 161〜173 個（鎖長 平均 4.7〜5.1／最大 7） |
| 鎖切れ率 | 平均 8.7〜12.5%、**鎖切れゼロのサンプルは 0.1〜3.7%** |
| QPU アクセス時間 | 0.13s（num_reads=1000）／0.77s（5000） |

品質が落ちる理由として2つが実測から見える。

1. **鎖切れ**：ほぼ全サンプルでどこかの鎖が切れており、多数決で補正された値が読まれている。
   論理 QUBO の解としての信頼度がそもそも低い。
2. **係数のダイナミックレンジ 896 倍**：予算制約ペナルティは重み 32 のスラック変数と
   掛かって数千になる一方、識別したい項目価値の差は 0.15〜2.4 しかない。
   QPU は最大絶対値が 1 になるよう自動スケールしてから磁束を印加するため、
   **価値の差がハードウェアの制御誤差（ICE）に埋もれる**。
   倍精度で計算する neal では起きない、実機特有の問題。

> 7.1 で「ペナルティ係数の桁差は SA の品質のボトルネックではなかった」と結論したが、
> **実機ではこの桁差が別の経路（アナログ精度）で効いてくる**。
> 桁差の解消は SA には無意味でも、実機で解くなら必要になる。

改善の方向：スラック変数の重みを小さく分割して予算項の係数を圧縮する、
`--chain-strength` の調整、埋め込みの固定・再利用（`LazyFixedEmbeddingComposite`）。いずれも未着手。

### 7.3 規模に対する率直な評価

**この規模（候補27項目 = 2^27）では、古典手法が速度・品質の両面で上回る**。
アニーリングの優位性は主張できない、というのが正直な結論。

前処理化（4.2）により、83%を占めていた前提違反サンプルは構造的に消え、
実行可能サンプルは **5000中4994件**まで上がった。しかしそれでも解の品質は
最適の 95% 前後で頭打ちであり、**実行可能率の改善は品質の改善に直結しなかった**。

## 8. 今後の展開

### 8.1 時間軸への拡張 ★本命の発展方向

現在の決定変数は `z_j`（項目 j を学ぶか）の**1添字**で、学習の順序を決めていない。
ここに時間軸を導入する。

```
z_{j,t} ∈ {0,1}   … 項目 j を第 t 週に学習するか（t = 1..24）
```

**これによって得られるもの**

| 現状 | 拡張後 |
| --- | --- |
| 前提科目は集合の包含関係（`z_Unity ≤ z_C#`） | **本来の順序制約**（C# を Unity より前の週に完了） |
| 週あたりの負荷は考慮されない | **週次の時間上限**（週30h を超えない） |
| 「何を学ぶか」だけ | **「いつ学ぶか」まで出力** ＝ 実用的な学習カレンダー |
| 学習の中断・並行が表現できない | 複数項目の並行学習・分割学習を表現できる |

**前提科目の順序制約**は、完了週を用いて次のように書ける。

```
Σ_t t · z_{child,t} ≥ Σ_t t · z_{parent,t} + 1     （親は子より前の週）
```

**問題規模**

```
現状:   27項目               = 27変数
拡張後: 27項目 × 24週        = 648変数（＋各種スラック）
```

**なぜこれが第7章の課題への回答になるか**

現状の 2^27 という探索空間は、厳密解が 1.8 秒で解けてしまう規模だった。
648 変数（2^648）に拡張すれば厳密解・貪欲法は現実的な時間で解けなくなり、
**メタヒューリスティクスとしてのアニーリングの意義が初めて成立する**。
同時に、週次制約と順序制約という「二次形式に落としにくい制約」が加わるため、
定式化の技術的な見どころも増える。

> **前提条件は解消済み**：先に片付けるべきとしていた前提科目の前処理化（#5）と
> ペナルティ係数の適正化（#8）は完了した。ただし #8 の結果、桁差は品質の
> ボトルネックではなかったと分かっている（7.1）。**残る品質差の原因を切り分けないまま
> 変数数を24倍にすると、悪化の原因が特定できなくなる**点には注意が必要。

## 9. まとめ

- 実問題（学習計画）の3要素——**予算・前提科目・組み合わせ効果**——を扱う推薦モデルを構築した
- **制約の置き場所を実測に基づいて仕分けた**：予算・シナジーは QUBO、
  前提科目は前処理のハード制約へ（サンプルの83%が前提違反という実測が根拠）
- 前処理化により QUBO は **53変数 → 34変数**に削減され、実行可能サンプルは **5000中4994件**になった
- 適性 u は前処理で **V_j(u) と候補集合 C(u)** に畳み込まれる構造を明確化した
- **仮説を立てて棄却した**：ペナルティ係数の桁差（A=30.050 vs 目的差 0.15〜2.4）が品質を
  損なっているという見立てを、A を 2.424 まで下げて検証した結果、達成率は 94.3% → 94.9% と
  ほぼ変わらず、**桁差はボトルネックではなかった**と結論した（7.1）
- 一方で**解の品質は最適の 94.9%**（5シード平均）に留まり、原因は未特定のまま残っている
- **実機 D-Wave QPU（Advantage_system6）でも解いた**。動作と埋め込みは確認できたが
  達成率は 75.1% で neal を下回る。鎖切れ（ほぼ全サンプル）と、
  係数レンジ 896 倍によるアナログ精度不足という**実機固有の壁**が可視化された（7.2）
- 時間軸を導入した `z_{j,t}` への拡張により、アニーリングの意義が成立する規模へ発展できる見通しを得た

**定式化と設計方針は固まり、有力な仮説を1つ実測で棄却できた。** それが現時点の到達点。

### A.4 前提科目（AND 15件 / OR 8件）

**AND**（親を全て必要とする）の例
- 機械学習 → Python基礎 ＋ 統計・数学
- クラウド(AWS等) → Linux基礎 ＋ ネットワーク基礎
- Unity → C# ／ Unreal Engine → C++
- フロントFW → JavaScript/TS → HTML/CSS（連鎖）

**OR**（いずれか1つ以上）の例
- Git → JS/TS・バックエンド言語・Swift/Kotlin・Flutter/RN・Python基礎 のいずれか
- モバイルUI → Swift/Kotlin か Flutter/RN
- アルゴリズム → 4言語のいずれか

`validate_prerequisite_data()` により、存在しない項目名の参照と OR 選択肢0件を**起動時に検査**している。

### A.5 係数の妥当性について

**すべて仮値**であり、根拠データに基づく調整は今後の課題（8.2-3）。
ただし A.1・A.2・A.3 で挙げた3点は、値の妥当性以前の**構造的な問題**であり、
質疑で指摘される可能性がある。

# プレゼン資料：盛り込む内容

IT学習項目推薦システムの発表用メモ。
主題は **「実問題を QUBO へ落とし込む定式化」＋「前提科目を前処理でハード制約として担保する設計」**。
解の品質は現状の課題として率直に提示する。

> - **分野プロファイルは O*NET（米国労働省の職業データベース）由来の実データに差し替えた**
>   （4.10、要件定義 §13）。あわせて分野相性の式に正規化を入れた。
>   シナジー値は引き続き**仮の値**で、根拠データに基づく調整は今後の課題（issue #12）。
>   ペナルティ係数は限界寄与基準で導出済み（4.7、issue #8）。
> - **前提科目の扱い**：「前処理でハード制約として担保（目的関数に含めない）」で
>   **実装済み**（要件定義 §3.5、issue #5）。ペナルティ項方式との比較は経緯として 4.8 に残す。
> - **OR前提は廃止した**（4.9）。前提科目は AND（全親必須）のみ。
>   その後、親が一意に定まる必須依存を6本追加した（要件定義 §11）。
>   学習項目の再定義を経て、現在は**依存22本／子項目19件**である。
>   本資料の数値は特記なき限り**廃止後の再測定値**である。

---

## 1. 課題設定

**「限られた学習時間で、何をどの順に学べば最も効果的か」** を決めたい。

- IT分野は多岐にわたり、初学者が独力で学習計画を立てるのは難しい
- 単に「価値の高い項目を並べる」だけでは駄目な理由が3つある
  1. **時間予算**がある（週30h × 24週 = 720h など）
  2. **前提科目**がある（Unity を学ぶには C# が要る／機械学習には Python と統計が要る）
  3. **組み合わせ効果**がある（Docker と AWS は相乗／Unity と Unreal Engine は非効率）

→ 個々の項目を独立に評価できない **組合せ最適化問題**。

---

## 2. なぜ QUBO なのか

| 要素 | 表現 | 置き場所 |
| --- | --- | --- |
| 項目単体の価値 | 線形項 | QUBO 目的関数 |
| 組み合わせ効果（シナジー） | **二次項** | QUBO 目的関数 |
| 時間予算 | ペナルティ項（ソフト制約） | QUBO 目的関数 |
| **前提科目** | **ハード制約** | **前処理**（★確定方針） |

特に **負のシナジー**（同時に学ぶと非効率）は、項目を独立に評価する
線形モデルでは原理的に表現できない。二次項を持つ QUBO の必然性がここにある。

一方、**前提科目は「破ってよい度合い」が存在しない論理制約**なので、
ペナルティで抑え込むのではなく前処理で構造的に保証する（第4.2節）。
「何をペナルティにし、何をペナルティにしないか」の切り分け自体が設計判断である。

## 3. システム全体像

```
適性5軸ベクトル u（ユーザー入力）
  ↓  平均二乗距離 ÷ 分野ごとの距離上限（正規化）
各IT分野との相性 fs（10分野）
  ↓  閾値 0.60 未満を除外（0件なら最上位1分野を残す）
分野関連度 fr
  ↓  所属分野の関連度を合計
学習項目価値 V(u)（38項目）
  ↓  価値0の項目を除外＋前提科目クロージャ
候補集合 C(u)（デモ条件で10項目）
  ↓  前提科目の担保（前処理・ハード制約）★確定方針
  ↓  予算・シナジーのみを QUBO 化（19変数・実測）
シミュレーテッド・アニーリング
  ↓
実行可能解の抽出 → 推薦結果
```

※ 旧実装では前提科目も QUBO 内のペナルティ項だった（53変数）。第4.8節参照。

**構成**（Python / dimod / neal）

| ディレクトリ | 役割 |
| --- | --- |
| `config/` | 係数・データ定義（分野・項目・シナジー・前提科目） |
| `inputs/` | ユーザー入力（CSV で適性と学習時間を指定） |
| `calculation/` | QUBO 構築・アニーリング |
| `output/` | テキストレポート・グラフ2枚 |

データと計算ロジックを分離してあるため、**係数の差し替えだけでモデルを調整できる**。

## 4. 定式化 ★発表の中心

### 4.1 適性はどこに入るか ★頻出質問への先回り

ハミルトニアン（4.4）だけを見ると適性 u が現れないが、
**u は前処理で線形係数 V と候補集合 C に畳み込まれている**。

```
D_f     = (1/5) Σ_a max(F_{f,a}, 1−F_{f,a})²               … その分野から最も遠い人までの距離
fs_f(u) = clip( 1 − (1/5) Σ_a (F_{f,a} − u_a)² / D_f, 0, 1 ) … 分野相性（完全一致=1／最遠=0）
fr_f(u) = fs_f  (fs_f ≥ 0.60) / 0  (fs_f < 0.60)           … 低相性分野の足切り
V_j(u)  = Σ_{f ∈ fields(j)} fr_f(u)                         … 項目価値
```

**適性 → 分野相性 → 項目価値** と伝播し、線形項の係数として効く。

例）u = [0.5, 1.0, 1.0, 1.0, 1.0] のとき、SQL/データベース（2分野に所属）は

| 所属分野 | プロファイル F_f | D_f | 相性 fs_f |
| --- | --- | --- | --- |
| バックエンド | [0.25, 0.75, 0.25, 0.25, 0.25] | 0.563 | 0.356（0.60未満 → 足切り） |
| データ/ML | [0.25, 1.00, 0.00, 1.00, 0.75] | 0.825 | 0.727 |

→ V_SQL = 0 + 0.727 = **0.727**

**`D_f` で割る正規化がこの改訂の要点**である（4.10）。割らないと、プロファイルが
中央（0.5）に寄った分野ほど中身と無関係に誰にでも高い相性を返してしまう。

**何がユーザー依存で、何が共通か**

| | 適性 u への依存 |
| --- | --- |
| 線形係数 V_j(u) | **依存する**（ユーザーごとに変わる） |
| **候補集合 C(u)** | **依存する**（V=0 の項目は候補外。デモ条件では 38項目 → 10項目） |
| 二次係数 S_ij | 依存しない（全ユーザー共通） |
| 予算制約 | 依存しない |
| 前提科目 | 依存しない |

適性は係数だけでなく**問題サイズそのものを変える**。
逆に、この設計では適性が「組み合わせの好み」には影響しない
（誰にとっても Docker × AWS は +0.3）。S_ij(u) への拡張は将来の論点。

### 4.2 前提科目のハード制約担保 ★設計の主役

**方針（確定）**：前提科目は QUBO の目的関数（ペナルティ項）に**含めず**、
前処理段階でハード制約として保証する。

- AND前提：子を選ぶなら親を**すべて**選ぶ（z_child ≤ z_parent）。**前提科目はこの1種類のみ**（4.9）

**なぜペナルティにしないか（実測に基づく判断）**

旧実装（ペナルティ方式）の 5000 サンプルの内訳：

| 判定 | 件数 | 割合 |
| --- | --- | --- |
| **前提科目違反** | **4168** | **83%** |
| スラック等式違反 | 207 | 4% |
| 予算違反 | 25 | 1% |
| 実行可能 | 797 | 16% |

**サンプルの83%が前提科目違反**で捨てられており、探索の大半が無駄になっている。
前提科目を構造的に保証すれば、この違反カテゴリは**定義上ゼロ**になる。

**QUBO 規模への効果（デモ条件・実測）**

| | 変数 | 二次項 |
| --- | --- | --- |
| 旧実装（前提科目＝ペナルティ項） | 53 | 653 |
| 前処理化後（現行） | **34**（−36%） | **561**（−14%） |

内訳：前提科目のペナルティに使っていた OR スラック19変数が丸ごと消える。

**担保機構（3段構え・実装済み）**

| 段階 | 内容 |
| --- | --- |
| ① 候補集合の制限 | 前提クロージャ込みの最小時間が予算を超える項目を候補から外す |
| ② 候補展開 | 候補項目が必要とする前提科目を候補へ追加する |
| ③ 修復デコード | 各サンプルを前提充足の選択へ変換する（下方修復＋上方補完。第5章） |

**難所だった点**：前提科目は予算制約と結合する（子を選ぶと親の hours も消費する）ため、
単純な事前確定はできない。①で「前提クロージャ込みの最小時間」を使うことでこれを解いた。
OR前提の廃止（4.9）により、このクロージャは項目ごとに**一意**に定まるようになった。

### 4.3 決定変数

```
z_j ∈ {0,1}   (j ∈ C(u))   … 学習項目 j を学習計画に含めるか、含めないか
```

（一般には x_i と書かれることが多いが、本資料はコードに合わせ z とする）

**添字は 1 つだけ**。決めているのは「どの項目を学ぶか」という**集合**であり、
学習の順序・時期は決めていない。前提科目も順序制約ではなく**集合の包含関係**
（z_Unity ≤ z_C# は「C# を先に学ぶ」ではなく「C# も選ぶ」の意）。

厳密には **前提科目つき・シナジーつきのナップサック問題**であって、スケジューリング問題ではない。
（時間軸を持つ定式化への拡張は第8.1節）

これに加えて、予算不等式を等式化する**スラック変数**が入る（解の意味を持たない計算上の道具）。

| 変数 | 意味 | 個数（目標設計） |
| --- | --- | --- |
| `item_j` = z_j | 項目 j を学ぶか | 27 |
| `slack_k` | 予算の余り時間のバイナリ展開・第 k 桁 | 7 |
| | **合計** | **34** |

※ 旧実装ではさらに OR 前提用スラック 19 変数が加わり 53 変数だった（第4.8節）。
OR 前提そのものの廃止（4.9）では変数は減らない（すでに前処理化で消えていたため）。

### 4.4 目的関数（ハミルトニアン）

```
H(z) = − Σ_{j∈C(u)} V_j(u) z_j          … 線形項（項目価値。適性はここに入る）
       − Σ_{i<j} S_ij z_i z_j            … 二次項（シナジー。負値も可）
       + A ( Σ_j c_j z_j + s − B )²      … 予算制約（スラックで等式化）
```

- **前提科目のペナルティ項は含めない**（4.2 の前処理で担保。★確定方針）
- 二次項は i<j で走る（S は対称行列なので Σ_{i,j} と書くと二重計上になる）

### 4.5 予算制約：不等式 → 等式変換

QUBO は等式制約しか自然に表せないため、**スラック変数**を導入する。

```
Σ c_j z_j ≤ B    →    Σ c_j z_j + s = B    →    A ( Σ c_j z_j + s − B )²
```

`s` は `bounded_binary_weights(B)` によるバイナリ展開。
B = 72 に対し重み **[1, 2, 4, 8, 16, 32, 9]** の7変数で 0〜72 を過不足なく表現。
（単純な 2 冪だと 0〜127 まで表せてしまい無駄が出る。上限で打ち切るのが工夫点）

### 4.6 変数削減：最大公約数による時間圧縮

予算と候補項目の学習時間の GCD で単位化する。

```
g = gcd(720, {40, 90, 60, ...}) = 10
→ 720h = 72単位、40h = 4単位
```

スラック変数は **10個 → 7個** に削減される（実測値）。

```
B=720（圧縮なし）: [1, 2, 4, 8, 16, 32, 64, 128, 256, 209] … 10変数
B=72 （GCD圧縮）: [1, 2, 4, 8, 16, 32, 9]                  …  7変数
```

バイナリ展開なので変数数は log オーダーであり削減幅自体は 3 変数だが、
**ペナルティ項の係数の桁が 2 桁下がる**効果のほうが大きい
（予算制約の二次項は係数の積で効くため、数値的な安定性に直結する）。

### 4.7 ペナルティ係数

```
A = max_j ( V_j + Σ_i max(0, S_ij) ) × 1.01 = 2.227 × 1.01 = 2.250   … デモ条件の実測
      └─ 単一項目の限界寄与 ─┘
```

「**違反を防ぐのに必要な最小値**」から決める。予算を1単位超えた解からは、他の選択項目の
前提になっていない項目を1つ除去すれば実行可能化でき、そのとき失う報酬の主要項が
単一項目の限界寄与だからである（×1.01 は同点を避ける微小マージン）。

旧設計は `A = 報酬上限 + 1 = 30.050`（「いかなる制約違反も最大報酬を上回る損失」）で、
目的項の差 0.15〜2.4 に対し**1〜2桁大きかった**。現行は目的項と同じ桁に収まっている。

OR 前提の廃止（4.9）により、この限界寄与は**厳密な上界**になった。前提を持つ子の
条件付き価値が AND のみとなり、報酬がちょうど `V_c`（満額）で頭打ちになるためである。
したがって「`A >` 限界寄与 なら1単位違反の解は必ず実行可能解に負ける」と言い切れる。

**※ ただし桁差の解消は解の品質を改善しなかった（第7.1節）。**

### 4.8 旧実装との差分（経緯として簡潔に）

旧実装では前提科目もペナルティ項として QUBO 化していた
（AND は `A·z_child(1−z_parent)` の2項、OR は予算と同じスラック法で二乗ペナルティ化）。
**QUBO 化自体は実装・検証済み**だが、実測で**サンプルの83%が前提違反**となり
探索効率を大きく損なうことが分かったため、**前処理でのハード制約担保へ移行した**（4.2、issue #5）。

→ 「まず全部 QUBO に入れて動かし、実測に基づいて制約の置き場所を仕分けた」という
**設計判断の物語**として1枚で話す。

### 4.9 OR 前提の廃止 ★モデルの簡素化

前提科目には当初 AND（全親必須）に加えて **OR（選択肢のうち1つ以上、`z_child ≤ Σ z_parents`）**
が 8 件あったが、**廃止して AND のみとした**（その後、必須依存を6本追加。下記）。

**廃止した OR 関係**

| 子項目 | 選択肢だった親 |
| --- | --- |
| Git | JS/TS・バックエンド言語・Swift/Kotlin・Flutter/RN・Python基礎 |
| 開発環境/ターミナル | JS/TS・バックエンド言語・Swift/Kotlin・Flutter/RN |
| アルゴリズム | バックエンド言語・Python基礎・C#・C++ |
| SQL/データベース | バックエンド言語・Python基礎 |
| モバイルUI ／ アプリ設計 | Swift/Kotlin・Flutter/RN |
| 3Dグラフィックス ／ ゲーム数学・物理 | C#・C++ |

**廃止の理由**

1. これらは「必ず必要」ではなく「**あると効く**」弱い依存であり、
   ハード制約ではなく**シナジー `S_ij` で表すべき関係**だった
   （実際 `config/synergy.py` には「前提科目に近いが必須ではない」ペアが既に入っており、概念が二重）
2. 条件付き価値の分母 `min(m,2)` が**近似**でしかなく、探索の誘導が偏っていた
3. 予算枝刈り・修復デコードの**分岐処理の大半が OR 側**にあった

**効果**

| | 廃止前 | 廃止後 |
| --- | --- | --- |
| 条件付き価値 | AND は厳密／OR は近似（`min(m,2)`） | **すべて厳密**（近似項なし） |
| ペナルティ係数 A の根拠 | 限界寄与は厳密な上界ではない | **厳密な上界**（4.7） |
| 予算枝刈り | 候補展開の前後に2回 | **前に1回**（親のクロージャは子の部分集合） |
| 前提クロージャ | 選択肢ごとに分岐して最小値を探索 | **一意に定まる** |
| QUBO 規模 | 34変数 / 二次項 561 | **変化なし** |
| SA の達成率（12シード） | 94.6% | **96.2%**（7章） |

QUBO 規模が変わらないのは、**予算制約のペナルティ項が全変数ペアに二次項を張る**ため、
OR 由来の二次項を除いてもペアの本数は変わらず係数だけが変わるからである。

> **副作用（正直に言う）**：OR前提が禁じていた選択が実行可能になった。
> 当時のデモ条件の厳密最適解は `モバイルUI` を Swift/Kotlin・Flutter/RN のどちらも選ばずに含み、
> 「モバイル言語を学ばずにモバイルUIを学ぶ」という不自然な学習計画になっていた。
> **この副作用は解消済み**——必須依存は AND へ移し（下記）、残りの弱い依存はシナジーとして
> 入れ直した（モバイルUI × Swift/Kotlin +0.5、モバイルUI × Flutter/RN +0.5 など。付録 A.3）。

**その後の対応：必須依存を AND へ6本追加（要件定義 §11。追加時点で依存 17 → 23本、
子項目 15 → 20件。その後の学習項目の再定義を経て、現在は依存22本 / 子項目19件）**

AND は全親必須なので、**親が一意に定まる依存だけ**が移せる。

| 追加 | 根拠 |
| --- | --- |
| WordPress ← HTML/CSS | テーマ編集は HTML/CSS なしに成立しない |
| SEO/サイト運営 ← HTML/CSS | オンページ SEO は meta / 構造化データの理解が前提 |
| 画像編集 ← デザインツール(PS/AI) | 編集ツールなしに工程が存在しない |
| 3Dグラフィックス ← ゲーム数学・物理 | 座標変換・ベクトル・行列が前提 |
| Git ← 開発環境/ターミナル | Git は CLI ツール。ターミナル操作が前提 |
| テスト自動化 ← テスト技法(JSTQB) | 自動化の対象は設計済みのテストケース |

3Dグラフィックスと Git は OR を廃止した子項目だが、**廃止した選択肢とは別の親**を与えている。
「言語のうちいずれか」は AND にできないが、「ゲーム数学・物理」「開発環境/ターミナル」は
選択の余地がないため AND として書ける。

一方、**モバイルUI・アプリ設計・SQL/データベース・アルゴリズムは移していない**。
親が選択制であり、AND にすると「Swift/Kotlin と Flutter/RN を両方必須」という
誤った制約になるためである。上の副作用はシナジー側で扱う課題として残る。

### 4.10 分野プロファイルの実データ化と相性の正規化 ★係数の根拠づけ

「係数は仮値」という最大の弱点のうち、**分野プロファイル F（10分野×5軸=50値）を実データに置き換えた**。

**きっかけは値そのものではなく、式の構造的な偏りだった。**
5軸の回答は◎○×の3択なので、ありうる回答は `3^5 = 243` パターンしかない。
この全数に対して旧式 `fs = 1 − (1/5)Σ(F−u)²` の平均を取ると、恒等式

```
E_u[fs_f] = 0.8333 − (1/5) Σ_a (F_{f,a} − 0.5)²
```

が成り立つ。**分野の平均相性は中身ではなく「プロファイルの極端さ」だけで決まる**——
つまり中央（0.5）に寄せた分野ほど誰にでも高得点を返し、
**性格像を鮮明に書いた分野ほど推薦されにくくなる**。実測でも、

| 分野 | 極端さ | 243人中 fs≥0.75 | 1位回数 |
| --- | --- | --- | --- |
| モバイルアプリ（旧 `[0.3,0.7,0.7,0.6,0.7]`） | 0.034 | **71.6%** | **55** |
| グラフィックデザイン／インフラ | 0.186 | 29.6% | 24／15 |

となっており、非クリエイティブ・運用志向の回答者にモバイルアプリが最高相性で出ていた。

**対処①：分野ごとの距離の上限 `D_f` で正規化する**（4.1 の式）。
全分野で「完全一致=1／最も遠い人=0」が成立し、閾値の意味が分野間で揃う。
分野平均のばらつきは **0.152 → 0.059**。

**対処②：閾値を超える分野が0件なら最上位1分野を残す**。
候補0件で `RuntimeError` になる回答パターンが **15/243 → 0** になった（実回答 r5 が該当していた）。

**対処③：50値を O*NET（米国労働省の職業データベース）から導出する**。

| 5軸 | O*NET 記述子（各3〜4本の平均） |
| --- | --- |
| クリエイティブ | Work Styles: Innovation / Thinking Creatively / Originality / Fluency of Ideas |
| ロジカル | Analytical Thinking / Investigative / Deductive・Inductive Reasoning |
| 作る↔運用 | Interests: Artistic − Conventional |
| 数学 | Knowledge・Skill: Mathematics / Mathematical Reasoning / Number Facility |
| 計画性・正確さ | Attention to Detail / Dependability / Information Ordering / Conventional |

Work Styles は**職業ごとのパーソナリティ重要度そのもの**（Attention to Detail ≒ 誠実性、
Innovation ≒ 開放性）、Interests は **Holland の RIASEC**。
指標ごとにzスコア化 → 軸ごとに平均 → min–max 正規化 → 0.25刻みへ丸める。

**データが直感を否定した例**（そのまま採用した）

| --- | --- | --- |

## 5. 実装上の工夫：修復デコードと実行可能解の抽出

アニーリングの**最低エネルギー解をそのまま採用してはいけない**。低エネルギー側にも制約違反解が混ざる。
現行実装は各サンプルを**修復デコード**してから採用候補にする。

1. **下方修復**：前提が欠けている子項目を取り除く（項目が減るだけなので予算を新たに破らない）
2. **上方補完**：代わりに不足している親を足す解も試し、予算内なら候補に加える
   （高価値の子項目を捨てずに済む解を拾うため）
3. 修復後の選択に対して予算 `Σ h_j z_j ≤ T` を検査する

修復後の選択は定義上すべて前提を満たすため、**前提違反を理由にサンプルが捨てられることはない**。
残る検査は予算のみになる。

順位付けは**QUBOエネルギーではなく、修復後の真の目的関数値** `Σ V_j z_j + Σ S_ij z_i z_j` で行う。
エネルギーは修復前のビット列に対応する値であり、修復で項目が除かれると実際の価値とずれるため。
さらに採用後、予算と前提科目を**再検査**する二重の安全機構を設けた。

**効果**：旧実装（ペナルティ方式）では実行可能解が 5000中 **797件（16%）** だったのに対し、
現行実装では **5000中 4994件（99.9%）**。83%を占めていた前提違反が構造的に消えた。
ただし第7章のとおり、この改善は**解の品質の改善には直結していない**。

→ レポートの【実行可能サンプル数】【前提科目を修復したサンプル数】がこの機構の効きを示す。

> **注意**：分野プロファイルの改訂（4.10）でデモ条件の採用分野が2件に絞られ、
> 探索空間は 2^27 → **2^10** になった。`num_reads=5000` で毎回最適に届くのは
> 「SA が良くなった」からではなく**問題が小さくなったから**である。

（比較の測定スクリプトは `tools/exact_bb.py` としてリポジトリに収録。検証専用ツールであり、

（42, 1, 7, 123, 2024, 3, 11, 99, 256, 777, 1234, 31337）で測る。
一般に単一シードでは値がばらつくので、**単一シードの値で比較してはいけない**）

- **最適解との差**：最適解は `Git`(30h) と `開発環境/ターミナル`(10h) を追加で含む。

- `num_reads` を 5000 にすると12シードすべてが最適に到達する。
  **ただしこれは分野プロファイルの改訂（4.10）で探索空間が 2^27 → 2^10 に縮んだ結果**であって、
  SA が良くなったわけではない
- 改訂前（採用6分野・候補27項目）は 12シード平均 96.2%（18.137 / 18.850）で頭打ちだった。
  **問題を元の規模に戻したうえでの再測定が必要**である（8.2-5）

### 7.1 検証したが外れた仮説：ペナルティ係数の桁差（issue #8）

当初の見立てはこうだった——「ペナルティ係数 `A = 30.050` に対し目的項の差はわずか 0.15〜2.4。
**制約項が目的項より1〜2桁大きく**、エネルギー地形が制約充足に支配されて、
実行可能解どうしの優劣をアニーラーがほとんど識別できていない」。

そこで A を「違反を防ぐのに必要な最小値」（単一項目の限界寄与基準、4.7）へ下げ、
30.050 → 2.424 と**桁差を解消した上で再測定した**。

| A | 42 | 1 | 7 | 123 | 2024 | 5シード平均達成率 |
| --- | --- | --- | --- | --- | --- | --- |
| 30.050（旧・報酬上限+1） | 18.650 | 17.000 | 17.700 | 17.250 | 17.350 | **94.3%** |
| 2.424（新・限界寄与×1.01） | 17.950 | 18.000 | 17.100 | 17.800 | 17.650 | **94.9%** |

※ この表は **OR 前提の廃止前**の測定値（分母は当時の厳密最適 18.650）。
廃止後の同条件は 5シード平均 **96.3%**（18.150 / 18.850）で、A に関する結論は変わらない。

さらに `penalty_margin` を振って A を 2.4〜29.8 の範囲で連続的に変えても、
達成率は 91.6〜95.8% の間で**単調な傾向を示さない**（＝シード間ばらつきに埋もれる）。

> **結論：桁差は解の品質のボトルネックではなかった。**
> 「制約項が大きすぎて実行可能解どうしの優劣を識別できない」という見立ては、実測で支持されなかった。
> A の適正化そのものは数値的な健全性（二次項の係数の積が小さくなる）として意味があるが、
> **品質改善の手段ではない**。

品質差の原因は別にあると考えられる。当初の候補は (a) 条件付き価値による OR 前提の近似、
(b) 修復デコードが探索空間と真の目的関数の対応をずらしていること、
(c) そもそも SA がこの規模のナップサック型問題を苦手とすること、の3つだった。

**(a) は OR 前提の廃止（4.9）で消えた**。近似項がなくなり条件付き価値は厳密になったが、
達成率は 96.2% で**依然として最適に届かない**。残る原因は (b) (c) に絞られる。

### 7.2 実機 D-Wave QPU での実測（Advantage_system6）

> **この節の数値は OR 前提の廃止前の測定値**。廃止で QUBO の変数数・二次項数・
> ダイナミックレンジは変わらない（34変数／561／896倍）ため、埋め込みと鎖切れに関する
> 所見はそのまま有効だが、達成率の分母は 18.650 → 18.850 に変わっている。再測定は未実施。

`python main.py --backend qpu` で同じ QUBO を実機へ投げた。**動くことは確認できたが、
品質は neal を大きく下回った**（4回平均 14.000／達成率 75.1%、単発では 12.650〜15.950）。
`num_reads` を 1000 → 5000 に増やしても 15.600 で、**サンプル数はボトルネックではない**。

| 指標 | 実測値 |
| --- | --- |
| 埋め込み | 34 変数の完全グラフ K34 → 物理量子ビット 161〜173 個（鎖長 平均 4.7〜5.1／最大 7） |
| 鎖切れ率 | 平均 8.7〜12.5%、**鎖切れゼロのサンプルは 0.1〜3.7%** |
| QPU アクセス時間 | 0.13s（num_reads=1000）／0.77s（5000） |

品質が落ちる理由として2つが実測から見える。

1. **鎖切れ**：ほぼ全サンプルでどこかの鎖が切れており、多数決で補正された値が読まれている。
   論理 QUBO の解としての信頼度がそもそも低い。
2. **係数のダイナミックレンジ 896 倍**：予算制約ペナルティは重み 32 のスラック変数と
   掛かって数千になる一方、識別したい項目価値の差は 0.15〜2.4 しかない。
   QPU は最大絶対値が 1 になるよう自動スケールしてから磁束を印加するため、
   **価値の差がハードウェアの制御誤差（ICE）に埋もれる**。
   倍精度で計算する neal では起きない、実機特有の問題。

> 7.1 で「ペナルティ係数の桁差は SA の品質のボトルネックではなかった」と結論したが、
> **実機ではこの桁差が別の経路（アナログ精度）で効いてくる**。
> 桁差の解消は SA には無意味でも、実機で解くなら必要になる。

改善の方向：スラック変数の重みを小さく分割して予算項の係数を圧縮する、
`--chain-strength` の調整、埋め込みの固定・再利用（`LazyFixedEmbeddingComposite`）。いずれも未着手。

### 7.3 規模に対する率直な評価

**この規模（候補は多くて27項目 = 2^27、分野プロファイル改訂後のデモ条件では 2^10）では、
古典手法が速度・品質の両面で上回る**。厳密解が 1 秒未満で出てしまう。
アニーリングの優位性は主張できない、というのが正直な結論。

前処理化（4.2）により、83%を占めていた前提違反サンプルは構造的に消え、
実行可能サンプルは **5000中4994件（12シード平均）** まで上がった。
OR 前提の廃止（4.9）でモデルの近似も取り除き、分野プロファイルも実データにした（4.10）。
それでも**係数やモデルの改善はいずれも「解の品質」の改善には直結していない**。
規模そのものを上げない限り（8.1）、この結論は変わらない見込みである。

## 8. 今後の展開

### 8.1 時間軸への拡張 ★本命の発展方向

現在の決定変数は `z_j`（項目 j を学ぶか）の**1添字**で、学習の順序を決めていない。
ここに時間軸を導入する。

```
z_{j,t} ∈ {0,1}   … 項目 j を第 t 週に学習するか（t = 1..24）
```

**これによって得られるもの**

| 現状 | 拡張後 |
| --- | --- |
| 前提科目は集合の包含関係（`z_Unity ≤ z_C#`） | **本来の順序制約**（C# を Unity より前の週に完了） |
| 週あたりの負荷は考慮されない | **週次の時間上限**（週30h を超えない） |
| 「何を学ぶか」だけ | **「いつ学ぶか」まで出力** ＝ 実用的な学習カレンダー |
| 学習の中断・並行が表現できない | 複数項目の並行学習・分割学習を表現できる |

**前提科目の順序制約**は、完了週を用いて次のように書ける。

```
Σ_t t · z_{child,t} ≥ Σ_t t · z_{parent,t} + 1     （親は子より前の週）
```

**問題規模**

```
現状:   候補27項目            = 27変数
拡張後: 27項目 × 24週         = 648変数（＋各種スラック）
```

**なぜこれが第7章の課題への回答になるか**

現状の 2^27 という探索空間は、厳密解が 1.8 秒で解けてしまう規模だった。
648 変数（2^648）に拡張すれば厳密解・貪欲法は現実的な時間で解けなくなり、
**メタヒューリスティクスとしてのアニーリングの意義が初めて成立する**。
同時に、週次制約と順序制約という「二次形式に落としにくい制約」が加わるため、
定式化の技術的な見どころも増える。

> **前提条件は解消済み**：先に片付けるべきとしていた前提科目の前処理化（#5）と
> ペナルティ係数の適正化（#8）は完了した。ただし #8 の結果、桁差は品質の
> ボトルネックではなかったと分かっている（7.1）。**残る品質差の原因を切り分けないまま
> 変数数を24倍にすると、悪化の原因が特定できなくなる**点には注意が必要。

   分野ごとの総時間が不均衡（付録参照）なため、
   粒度を揃えつつ項目数を増やす（8.1 の時間軸拡張と合わせて問題規模を上げる）
8. **流行項（トレンド）の導入**
   人気度を線形項に組み込む（データ源・スコア化は未定）
9. **実機 D-Wave QPU 向けのチューニング**（実行自体は 7.2 で実施済み）
   実機では達成率 75.1% と neal を下回る。スラック変数の重み分割による
   係数レンジの圧縮、鎖の強さの調整、埋め込みの固定・再利用で改善余地がある

## 9. まとめ

- 実問題（学習計画）の3要素——**予算・前提科目・組み合わせ効果**——を扱う推薦モデルを構築した
- **制約の置き場所を実測に基づいて仕分けた**：予算・シナジーは QUBO、
  前提科目は前処理のハード制約へ（サンプルの83%が前提違反という実測が根拠）
- 前処理化により QUBO は **53変数 → 34変数**に削減され、実行可能サンプルは **5000中4994件**になった
- 適性 u は前処理で **V_j(u) と候補集合 C(u)** に畳み込まれる構造を明確化した
- **仮説を立てて棄却した**：ペナルティ係数の桁差（A=30.050 vs 目的差 0.15〜2.4）が品質を
  損なっているという見立てを、A を 2.424 まで下げて検証した結果、達成率は 94.3% → 94.9% と
  ほぼ変わらず、**桁差はボトルネックではなかった**と結論した（7.1）
- **係数の根拠づけを1つ片付けた**：分野プロファイル50値を O*NET（米国労働省の職業データベース）
  由来の実データへ置き換え、あわせて**相性の式に潜んでいた構造的バイアス**——
  「中央に寄せたプロファイルほど誰にでも高得点を返す」——を正規化で取り除いた（4.10）。
  導出過程は全セル分を `docs/field_profile_rationale.md` に残してある。
  適性だけで計算した相性が、独立に申告された興味と 13分野中9分野で一致した
- 一方で**解の品質の問題は未解決のまま**である。プロファイル改訂でデモ条件の探索空間が
  2^27 → 2^10 に縮み、`num_reads=5000` なら12シードすべてが最適に届くようになったが、
  これは**問題が易しくなっただけ**であって SA が良くなったわけではない（7章）
- **実機 D-Wave QPU（Advantage_system6）でも解いた**。動作と埋め込みは確認できたが
  達成率は 75.1% で neal を下回る。鎖切れ（ほぼ全サンプル）と、
  係数レンジ 896 倍によるアナログ精度不足という**実機固有の壁**が可視化された（7.2）
- 時間軸を導入した `z_{j,t}` への拡張により、アニーリングの意義が成立する規模へ発展できる見通しを得た

**定式化と設計方針は固まり、有力な仮説を1つ実測で棄却し、係数を実データで裏づけた。**
残るのは「この規模ではアニーリングの優位性を主張できない」という一点であり、
その回答は係数の調整ではなく**問題規模の拡張**（8.1）にある——それが現時点の到達点。

### A.4 前提科目（AND のみ：子項目19件 / 依存22本）

**OR前提は廃止済み**（4.9）。現在は AND（親を全て必要とする）の1種類しかない。

**親が1つの例**
- Unity → C# ／ Unreal Engine → C++
- API設計 → バックエンド向け言語 ／ Firebase/Supabase → バックエンド向け言語
- Docker → Linux基礎 ／ 統計・数学 → Python基礎 ／ データ可視化 → Python基礎

**親が複数の例**
- 機械学習 → Python基礎 ＋ 統計・数学
- クラウド(AWS等) → Linux基礎 ＋ ネットワーク基礎
- テスト自動化 → Python基礎 ＋ テスト技法(JSTQB)

**連鎖する例**
- フロントFW(React等) → JavaScript/TS → HTML/CSS
- 3Dグラフィックス → ゲーム数学・物理 → アルゴリズム

**4.9 の後に追加した6本**（親が一意に定まる依存だけを AND へ移した。要件定義 §11）
- WordPress → HTML/CSS ／ SEO/サイト運営 → HTML/CSS ／ 画像編集 → デザインツール(PS/AI)
- 3Dグラフィックス → ゲーム数学・物理 ／ Git → 開発環境/ターミナル ／ テスト自動化 → テスト技法(JSTQB)

`validate_prerequisite_data()` により、存在しない項目名の参照と前提グラフの循環を**起動時に検査**している。

### A.5 係数の妥当性について

**分野プロファイル（A.1）は O*NET 由来の実データに差し替え済み**で、
50セルすべてに出典と導出過程がある（4.10、`docs/field_profile_rationale.md`）。
**シナジー（A.3）と前提科目（A.4）は引き続き仮値**であり、
根拠データに基づく調整は今後の課題（8.2-4）。

A.2・A.3 で挙げた点（分野ごとの総時間の不均衡、シナジーが項目価値より小さいこと）は
値の妥当性以前の**構造的な問題**であり、質疑で指摘される可能性がある。
